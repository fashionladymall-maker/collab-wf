# CHAT.md —— 在 WorkBuddy 聊天窗口里操作（执行端的约定）

用户不再使用命令行。用户在 WorkBuddy 聊天窗口里说话，执行端把话翻译成 wf 命令执行；需要用户决定的事，执行端主动呈报到聊天窗口；执行端不在场时，看板是用户唯一的信息来源。

## 1. 分工

| 承载 | 做什么 | 为什么 |
|---|---|---|
| 聊天窗口 | 用户发起、批准、暂停、继续、回退；执行端呈报待决事项与通知 | 留下用户原话作为凭据；用户已经在用 |
| 看板（只读） | 执行端不在场时，告诉用户现在在哪、要他决定什么、该回复哪句话 | 不依赖执行端在场 |

**看板不可写。** 它运行在本机端口上，本机任何程序都能访问它，一次点击无法证明是用户本人点的；而聊天窗口天然记录用户说了什么。用户需要“能点的东西”时，由 WorkBuddy 把呈报中的回复选项做成可点的快捷回复（点击等于发送那句话），这仍然经过聊天、留下原话。

## 2. 什么时候呈报

执行端每次被唤醒（用户发话或系统定时唤醒）都运行：

```bash
wf ask --new --mark-shown
```

有输出就把它原样发到聊天窗口；没有输出就什么都不说。去重规则在 wf 里：同一件事只呈报一次；仍未处理时，12 小时后再提醒一次。所以执行端不需要自己判断“刚才说过没有”，也不会每分钟刷屏。

必须呈报的情况（wf ask 自动包含）：等待用户决定（驱动器停下）、阻塞、已暂停、白名单或目标未批准（或批准后被改动）、需要用户确认的人工目标。只通知一次、不需要决定的：目标达成、额度用尽等待重置、某一步停留过久。

## 3. 呈报模板

wf ask 的输出就是模板，执行端不改写：

```
【需要你决定 · btc-quant · 决定码 K7P】
事项：需要你批准才能继续
现在：第 22 轮 · 等待用户决定
原因：以下内容需要用户批准后才会执行：……
你回复：「批准 K7P」；或回复：「暂停」
不处理会怎样：驱动器保持停住，不会自动继续
依据：评审结果与证据在看板“本轮执行”
```

如果 WorkBuddy 支持卡片或快捷回复，可以用 `wf ask --json` 的 items 渲染：标题、原因、回复选项（reply）、后果（consequence）。

## 4. 翻译用户的话

对照表在工具根目录的 intents.json。三条硬规则：

1. **批准类必须有码。** 用户说“批准 K7P”，执行端运行该码对应的命令（`wf ask --json` 里该项的 command），并把用户原话逐字放进 `--said`。用户只说“好的”“批准”而没有码时，不执行；回复当前的待决事项和它们的码，请用户说清是哪一件。
2. **执行端不发起批准类意图。** 批准、继续、确认、解除阻塞，只在用户本轮说了之后执行。暂停是例外：它让事情更安全，执行端发现异常时可以自行暂停，并立即呈报原因。
3. **`--said` 只能是用户原话。** 不概括、不补全、不代写。

码是由事项内容算出来的：事项变了（例如白名单又改了一行），码就变了，旧码会被拒绝。这防止的是“批准落到了错误的事项上”。它不能在技术上区分用户本人与同一台电脑上的其他程序，所以原话被逐字记录在事件流与决策日志里，用户可以在看板上核对每一次批准用的是什么原话。

## 4b. 聊天窗口里的面板

需要给用户看一眼全局时，运行 `wf panel`，把它输出的 HTML 小组件直接渲染进对话（WorkBuddy 支持内联渲染，不必开浏览器）。面板只放最小集：现在在哪、要不要他拍板（含决定码与照抄的话）、下一次自动检查时间。
分工：**回报**说“这一轮做了什么”，**面板**说“此刻的状态与待办”，两者不重复叙述过程。用户要完整的只读视图时，WorkBuddy 的内置浏览器打开 `http://127.0.0.1:8765/`（看板，只读）。

## 5. 回答“现在怎么样了”

用一两句话转述 `wf explain`：在哪一步、为什么、需要谁做什么；有待决事项就附上 `wf ask` 的内容。不贴整段输出，不贴命令。

## 5b. 手动发送后要登记 ref

过渡期（驱动器尚未全面接管）里,执行端手动把消息发到通道后,必须 `wf mark sent --ref <适配器返回的 ref>`。登记了 ref,系统定时 tick 就会在 WAIT_REPLY 持续轮询到回复到达,执行端不在场也不会空转;不登记 ref 会停在"需要用户"而没人接着查(第 25 轮那次空转 5 小时就是没登记)。

## 6. 执行端自己的活（不需要用户说）

健康检查（`wf doctor`、`wf schedule status`、`wf transport test`、`wf self-check`），有问题才呈报；看板进程的启停；开新对话（`wf bootstrap`，用户已授权；只有“把两个文件拖进新对话”需要用户，呈报时说清楚）；收到 Claude 交付的工具新版本时 `wf self-update`（它改变自动化自身，执行前在聊天里说一声）。

## 7. 执行端不在场时用户能看到什么

看板顶部的“需要你决定”（含决定码与要回复的话）、项目是否已暂停、驱动器最近一次运行与下一次自动检查的时间、定时器是否停了（超过 15 分钟没运行就变红）、看板自己是否在运行旧版本代码（红色告警）。这些都不依赖执行端在场。
