# CONTEXT.md —— Claude 的上下文：怎样记住一切、何时开新对话（1.5.5）

## 1. 给用户的说明

- Claude 在一个对话里能看到的内容有上限，对话越长，早期的细节越可能被压缩。所以我们不把“记忆”放在对话里，而是放在你电脑上的文件里，任何时候都能重建。
- 记忆靠四样东西：PROJECT.md（结论、决策、待办、失败台账）、git 历史（每个版本的代码）、对话记录与证据（三方逐字的对话、每条命令的原文、页面快照）、工具文档（工作规则）。它们都在本机，看板上能看到。
- 为什么页面上没有 Projects：Projects 的知识库要上传文件，而我们的通道只能下载、不能上传；而且我们的状态每一轮都在变，Projects 更适合放不常变的资料。我们的做法相当于一个自动维护的 Project：开新对话时，执行端把 PROJECT.md、工作规则和文件清单作为第一条消息发给新的 Claude，Claude 按清单点名读取需要的文件，一两轮就能接上。本项目开局就是这样接上的，并且逐字节核对过。
- 什么时候开新对话：对话到了设定的轮数或字数，或者 Claude 的回复明显对不上已有的结论，或者通道降级了这个对话。开新对话由执行端完成，你不需要做任何事。

## 2. 记在哪里

| 内容 | 位置 | 谁维护 |
|---|---|---|
| 结论、决策、待办、失败台账 | PROJECT.md | Claude |
| 每个版本的代码 | 项目 git（每版一个标签）；工具 git（wf-vX.Y.Z） | wf apply、wf self-update |
| 三方逐字的对话 | workflow/transcript.jsonl（看板“对话记录”） | wf 自动写入；用户原话用 wf said |
| 每条命令的原文、退出码、耗时 | workflow/evidence/ | wf exec、驱动器自动写入 |
| 页面上的样子（文本与截图） | workflow/evidence/page/（看板“Claude 页面快照”） | 适配器写出，wf 收下 |
| 发生过什么 | workflow/events.jsonl、decisions.jsonl | wf 自动写入 |

## 3. 何时开新对话

满足任何一条就开（在两轮之间开：上一轮回报已发出、Claude 已回复、执行端验收完；不在命令执行中途开）：

1. 体量到上限：policy.json 的 max_conversation_turns（按已发出的消息计）或 max_conversation_chars（按收发正文计）。驱动器每轮累计这两个数，到了就停下（异常 conversation_full）。
2. 回复对不上：Claude 的复述与 PROJECT.md 不符，或者反复索要已经给过的内容。执行端判断，用 wf note 记下原因。
3. 对话被降级：通道把这个对话换成了别的模型或模式，而降级只对这个对话生效、不会恢复。执行端发现后开新对话。
4. 同一个问题连续两轮在 high 档没有解决：先换思路（PROCESS.md 第 3 节）；仍不行时开新对话，用 max 档。

Claude 无法测量自己的上下文占用，所以只用上面这些可观测的信号，不凭感觉。

## 4. 恢复包与送达

- 生成：wf bootstrap --reason "原因"（驱动器到上限时自动生成）。内容是一条说明消息，加上项目仓库 zip 与工具 zip。说明消息里有：WORKFLOW.md 与 PROJECT.md 全文、工作流当前位置与下一个计划节点、上一轮的回报清单与结论、工具与项目的文件清单（路径、字节数、sha256 前 12 位）、仓库指纹。
- 送达：通道只能发文字、不能上传附件，所以只发说明消息；两个 zip 留在本机作备份。新的 Claude 按文件清单点名要读的文件，执行端用 cat 或 sed -n 读出，原文随回报送达（回报按预算完整嵌入，放不下的自动续传）。
- 核对：新的 Claude 第一轮用文件清单的 sha256 逐字节核对能核对的内容，并重算仓库指纹；核对不上就以本机 git 与证据原文为准。
- 代价：接上需要一到两轮读文档；开发需要的代码按需再读，锚点只用读到的原文。

## 5. 开新对话的步骤（执行端）

1. 新建对话（带全部 settings）。
2. wf conv new --note "原因"（先做这一步：它把新对话的起点记为下一轮）。
3. 发送说明消息，档位用 max。
4. 收到回复后照常推进；驱动器之前因 conversation_full 停下的，用 wf approve 放行。
