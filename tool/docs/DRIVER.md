# DRIVER.md —— 驱动器：让协作流程自己跑

从 1.1.0 起，工作流不再需要执行端逐条敲命令。系统定时唤醒 `wf tick`（或单个项目的 `wf run`），驱动器读状态、做当前能做的事、记账，直到需要等待外部或需要用户为止。

## 1. 一次唤醒做什么

```
加锁（同一项目同时只有一个驱动器）→ 检查暂停与白名单 → 健康检查（声明的长期进程）
→ 循环：按当前状态调用对应处理 → 有进展就继续 → 等待外部 / 需要用户 / 时间用完就停
→ 记录本次做了什么、停在哪里、为什么 → 释放锁
```

退出码：0 有进展或无事可做；10 在等外部（Claude、计划节点、额度、退避）；20 需要用户；30 目标达成；1 工具内部错误。

各状态的自动处理：

| 状态 | 驱动器做什么 |
|---|---|
| 组织消息 | 计划节点到期：自动生成节点消息；回复中断：自动生成“从断点继续”；验收后：自动生成回报（含“需要注意”）；档位按角色规则；密钥扫描；对话体量达到上限则停下并准备恢复包 |
| 发送 | 全局限速；先落盘“发送意图”，再调用适配器发送；只有拿到“生成已开始”的正面证据才算发出（只有心跳按通道忙处理）；被拒退避重试；额度用尽进入等待额度重置 |
| 等待 Claude | 定时轮询适配器；完成后保存回复与交付文件；叶子被安全防护拒绝时自动回退到上一条健康消息并重发本轮消息；手动发出且未登记 ref 的轮次会停下提示 |
| 接收与解析 | 解析五个固定块与【驱动指令】；缺块就请 Claude 从断点继续（最多 2 次） |
| 执行前评审 | 每条命令过白名单与停止底线；版本包检查新增内容与版本号；可选的独立审查；有一项不通过就停下等用户 |
| 落地版本 | 门禁基线 → wf apply → 门禁复查；落地后回归则自动回退并回报；可选核对仓库指纹 |
| 执行与取证 | 逐条执行，每条前落盘“执行到第几条”；失败按异常字典处理 |
| 验收 | 按【驱动指令】中的判据逐项判定；运行目标检查；按“之后”决定回报、等待或空闲 |
| 等待计划节点 / 等待额度重置 | 到点自动继续 |
| 等待用户决定 / 阻塞 / 目标达成 | 不做任何事，说明需要谁做什么 |

## 2. 不会出现“状态说在做、其实没在做”

- 每次运行在 state.json 中登记进程号；看板实时核对它是否还活着。上一次运行被打断，下次运行会记录“驱动中断”并从记录处接续。
- 发送前先落盘发送意图。被打断后只轮询确认，绝不重发；通道没有任何“已接受或正在生成”的迹象时安全停机（F14）。
- 执行前先落盘当前命令。被打断的那条命令不会被重跑，记入回报由 Claude 决定。
- 落地版本中途失败会自动恢复工作区（F15）。
- 状态写入互斥（1.5.2）：手工 wf 命令与驱动器同时写状态时，在同一把状态锁内与磁盘合并，只写回各自改过的字段；事件序号在锁内分配，不会重复。驱动器每一步之前合并一次并检查暂停，手工 wf pause 不会再被覆盖。

## 3. 自主边界（写在代码里）

**白名单默认拒绝**：只有 workflow/policy.json 中、经用户批准的命令模式会被自动执行；其余一律停下等用户。
**停止底线（内置，项目无法关闭）**：资金、密钥、合规、实盘四类命令；版本包中新增的实盘开关、密钥赋值、提现转账调用。
**护栏命令只能由用户执行**：wf self-update、self-rollback、pin、policy、goals approve/confirm、approve、unpause、force、unblock、resume、undo、rollback、init。驱动器没有调用这些命令的路径，白名单也无法放行它们。
**会改变工作流状态的 wf 命令驱动器永远不执行**：apply、pin、wait、verify、goals check、self-update 等只能在驱动器之外手动执行；出现在回复中时，驱动器停下列为手动步骤，用户批准后跳过它们继续（F21）。只读的 wf 命令（version、fingerprint、doctor、status、explain、audit、decisions、effort 等）可以在白名单允许时自动执行。
**命令拼接与重定向需要批准**：; && || > < ` $( & 一律停下（2>&1 除外），防止在白名单命令后拼接任意命令；管道只允许接过滤命令（head、tail、grep、wc、sort、uniq、cut）。
**批准绑定内容**：policy.json、goals.json 的批准按 sha256 记录在 workflow/approvals.json（受保护，版本包无法覆盖）。内容一改动，批准立即失效，驱动器停止。
**熔断**：连续 3 轮验收未通过、连续 8 轮目标没有进展、每天自动发送超过 20 轮，都会停下等用户（数值在 policy.json 中设定）。

> 说明：这些限制能阻止驱动器自行越界，但无法在技术上区分“用户本人”和“同一台电脑上的其他程序”执行护栏命令。批准是一个有记录、可审计的动作，而不是密码学意义上的签名。

## 3a. 门禁与自动回退

policy.json 的 gates 是用户批准的检查（例如能否导入、能否编译、测试是否通过），版本包无法单方面修改：

```json
"gates": [{"name": "imports", "cmd": "python run_backtest.py --list", "pass": {"exit": 0, "contains": ["ema_trend_vol"]}}]
```

落地前先跑一遍作为基线，落地后再跑一遍。落地前通过、落地后失败，就是这个版本引起的回归：驱动器自动回退到上一版本，把该版本的标签改名为 vX.Y-reverted-时间，记入决策日志，并回报给 Claude。落地前就失败的门禁不会触发回退，只记入回报。

## 3b. 独立审查（可选）

transport.json 中配置 review 程序后，每个版本包落地前，驱动器把改动的 diff 交给它（TRANSPORT.md）。它来自执行端可以接入的另一个模型系列，结论只有三种：pass、concerns（写入“需要注意”）、block（停下等用户）。它不能代替门禁与判据，也不能单独放行任何东西。

## 3c. 档位、决策与复盘

每条消息的档位由 roles.json 的角色规则决定（DESIGN.md 第 7 节），角色、档位与理由写入轮次记录与决策日志。决策日志 workflow/decisions.jsonl 只追加不修改，记录档位选择、门禁结果、自动回退、熔断、对话体量、独立审查、等待节点等决定：`wf decisions --tsv`。`wf effort` 按档位与角色复盘轮次、通过率、消耗与耗时。

## 3d. 对话体量

policy.json 的 max_conversation_turns 或 max_conversation_chars 达到时，驱动器停下，并自动生成新对话恢复包（wf bootstrap）。用户开新对话后先 `wf conv new --note …`（它把新对话的起点记为下一轮，先发送会把说明消息那一轮排除在外），再上传 zip、发送说明消息，然后 `wf approve --note …`。1.6.4 起，policy.json 的 auto_new_conversation 为 true 时，这一步由驱动器完成（第 22 节）；没有开启或没有成功时照旧停下。

## 4. 目标与完成判据

workflow/goals.json 声明目标，每个目标是可执行判据（检查命令与通过条件）或人工判据（只能由用户确认）。只有用户批准后才生效：

```bash
wf goals                     # 进度
wf goals approve --note "已阅读并同意"
wf goals confirm G2 --note "已确认平台合规"
wf goals check               # 立即运行一次可执行判据
```

驱动器在每轮验收后运行可执行判据；全部通过（人工判据已确认、且目标定义已批准）即进入“目标达成”并停下。目标被改动后，之前的确认与检查结果全部失效。

## 5. 【驱动指令】：让回复可以被自动执行

Claude 的回复在五个固定块之外，增加第六块【驱动指令】，每行一个键：

```
发布：btc-quant-v0.12.zip        （本轮要落地的版本包，或“无”）
之后：回报 | 空闲 | 等待 2026-10-16T16:30:00+00:00 模拟盘第一周对账
验收 1：c1 exit=0 包含 "自检已通过"
验收 2：c2 exit=0 不含 "需重启" 匹配 "变更 \d+ 个文件"
指纹：00d7c558e45dcb25           （落地后仓库指纹应为此值）
超时：900                         （每条命令的超时秒数）
失败后继续：否
```

1.6.6 起还可以写“执行端 N：<事项>”列出写给执行端的事，以及“之后：等执行端”（第 24 节）。cN 指【本机执行】中第 N 条命令。【本机执行】只放驱动器可以执行的命令；工具升级、批准等需要人做的操作写在正文中，不放进命令块。没有判据的清单项记为“暂缓”，原文进入回报由 Claude 判断。（1.5.0 起：暂缓项按“文字中的 cN → 反引号中的命令原文 → 序号一一对应”自动关联证据；原文按预算完整嵌入，放不下的分片续传；键所在行前的列表编号会被容忍；指令块有内容却解析不出任何键时写进“需要注意”。）任何失败都会把“之后”改为回报。1.5.2 起：有判据的命令按判据判定，预期无匹配的检索写 exit=1，不算失败；整轮成败与熔断只计验收未通过的项和未关联到清单项的失败命令，没有判据的清单项由 Claude 看原文判断、不计入熔断。“需要用户决定”中只有显式标注“（前置）”的事项会让本轮停下等用户，“不阻塞”之类的字样不会。

## 6. 异常字典

工具根目录的 anomalies.json：症状 → 处置 → 次数上限 → 超限后的动作。项目可以在 workflow/anomalies.json 中追加规则（优先匹配）。处置包括退避重试、等待额度重置、回报给 Claude、请 Claude 从断点继续、按声明拉起进程、停下等用户、阻塞。没有匹配的情况一律安全停机并完整上报（UNKNOWN）。

## 7. 调度与唤醒

由系统定时器（不需要常驻进程）每隔几分钟运行一次：

```bash
wf schedule plist > ~/Library/LaunchAgents/local.collab-wf.tick.plist
launchctl bootstrap gui/$(id -u) ~/Library/LaunchAgents/local.collab-wf.tick.plist
wf schedule status               # 各项目驱动器最近一次运行；超过 3 个周期视为定时器可能停了
```

生成的配置每 5 分钟运行 `wf tick --max-seconds 540`，使用绝对路径的 Python，日志写入 local/tick.log（超过 5 MB 自动轮转）。

定时器的失败模式：电脑睡眠时 launchd 不运行，醒来后补跑一次（驱动器幂等，不会重复做事）；用户注销后 LaunchAgent 不运行；launchd 的环境变量很少，所以配置里写明 PATH 与 Python 的绝对路径；一次运行超过间隔时，下一次会因为项目锁而跳过；定时器停了时，看板的驱动器卡片会变红（超过 15 分钟没有运行），`wf schedule status` 也会提示。

wf tick 推进全部已接入的项目：可以立即行动的先做（按 wf.json 的 priority），等待中的轮询一次，需要用户的跳过；wf.json 中 "auto": false 的项目不推进。任何一个项目遇到额度用尽，其他项目也会暂停发送直到重置。驱动器只运行无界面的子进程，不操作鼠标键盘、不开窗口、不截屏；传输适配器也必须遵守这一点（TRANSPORT.md）。

## 7a. 手动发送与驱动器接管（缺口 7）

一轮消息如果是在驱动器之外手动发出的，驱动器默认认不出它（它靠 ref 轮询）。两种做法：手动发送时用 `wf mark sent --ref <适配器返回的 ref>` 登记，驱动器就能接管轮询；或者整轮手动走到底，用 `wf mark replied` 收尾。没有 ref 又没手动收尾时，驱动器会停下并说明，而不是误判为“看不到”。

## 7b. 叶子被拒的自动恢复（§10）

通道的安全防护有时会拒绝一条消息（空回复、stop_reason=refusal），且无法从这条消息继续。适配器在 poll 时返回 `status: refused` 和 `parent_ref`（上一条健康消息）。驱动器据此回退到那条消息、重新组织并重发本轮消息，不新增轮次。同一轮连续被拒超过两次就停下问用户（可能是消息内容本身触发了防护）。1.5.0 起次数可配置：policy.json 的 max_leaf_refusals（默认 2，保持原行为）。建议设为 0，第一次被拒就停下由人查看那条消息：原样重发绕不开触发原因，只会多耗额度。

## 8. 用户的三个单命令

```bash
wf pause --note "原因"        # 暂停（立即生效，驱动器不再推进）
wf undo --note "原因"         # 回退到上一个版本并暂停
wf unpause --note "原因"      # 恢复
```

接管：暂停后，所有手动命令照常可用；恢复前用 wf explain 确认状态。

## 9. 审计

```bash
wf explain                    # 现在卡在哪、为什么、需要谁做什么
wf panel                      # 聊天窗口内联面板（HTML 小组件）
wf audit --n 60               # 自动执行过的一切：规则、动作、依据、结果
```

看板顶部的“驱动器”卡片显示同样的信息，以及最近一次运行做了什么、是否仍在运行。

## 10. 启用步骤（每个项目一次）

1. 配置传输适配器（每台机器一次）：local/transport.json，见 TRANSPORT.md；`wf transport` 检查。
2. Claude 交付 workflow/policy.json 与 workflow/goals.json；用户审阅后 `wf policy approve` 与 `wf goals approve`。
3. 系统定时器运行 `wf tick`。
4. 发起：`wf kick --message 任务文件`，或等计划节点到期。

## 11. 1.5.0 的可靠性约定

- 块标题必须位于行首（前面可有空白或 #、*、>、- 等标记）。同名标题出现多次时，按约定顺序取“在上一个块之后最早出现”的那个；只在行中间出现时退回旧规则并提示。正文中顺带提到块名，不会再顶掉真正的命令块。
- 回报原文：清单项没有判据时，按“文字中的 cN → 反引号中的命令 → 序号一一对应”关联证据；未关联的命令也附原文。原文完整嵌入、每段只出现一次；整份回报约 32000 字符的原文预算放不下的部分，分片写入 workflow/outbox/carry.json，下一份回报自动先补发。想尽快清空，安排一轮不执行命令的回报即可。
- 回复归属：适配器在 poll 完成时返回 reply_parent。它与本轮发送的 ref 不同，说明取回的是对话里已有的旧回复，驱动器不收下、继续等待，连续 3 次（policy 的 stale_reply_polls）后按 stale_reply 停下。不提供时行为不变，记 reply_unverified 事件，wf doctor 提示。
- 执行接续：驱动器被打断后接续时，若被标记的那条命令在证据里已有退出码与结束时间，记 exec_resumed，不再误报“执行时被中断”。
- 事件序号：先写状态再追加事件；被打断时只会跳号，不会重号。wf doctor 检查重复、倒序与坏行。
- 额度：轮次记录中的额度为空时同时写明原因（usage_note）；usage.json 的有效期与 wf doctor 的判定统一为 10 分钟；连续 3 条以上为空时 wf doctor 报警。
- 升级核验：wf self-update 安装后核对磁盘版本、每个文件与版本包一致、升级前在运行的看板已以新版本运行；任何一项不通过，就把该版本的标签改名为 wf-vX.Y.Z-failed-时间，并自动回滚到升级前的版本。核验写在新版本的代码里，所以从 1.5.0 升级到之后的版本时才生效；从 1.4.x 升到 1.5.0 这一次，需要手动核对 wf version、wf doctor 与 wf self-check。
- 无附件续接：wf bootstrap 的说明消息末尾附工具与项目的文件清单。通道不能上传附件时，Claude 据此点名读取。

## 12. 1.5.1 发送结果不明的处置

- 适配器超时先 SIGTERM、宽限后再 SIGKILL，并通过 WF_ADAPTER_TIMEOUT_S 告知上限（TRANSPORT.md 末节）。
- 发送结果不明（SEND_UNKNOWN）：默认照旧阻塞。policy.json 设 "send_unknown_wait": true 后改为 SEND_UNKNOWN_WAIT：保留发送意图，退避约一小时反复轮询确认，确认已送达就接续等待回复，仍不明再阻塞。任何情况下都不自动重发。
- 阻塞之后：想再核对一次用 wf unblock --to SEND；确认没有送达、需要重发用 wf resend（决定码加原话）。不要手改 state.json。
- 通道报忙：最可能的就是自己的上一条消息在生成。第 40 轮的回复用了 23 分钟，其间会话里看不到任何变化。
- wf note：本轮回报生成之后写的备注，会随下一份回报发出，写入时会提示。
- wf self-check 归为只读命令，驱动器可以直接执行（白名单 policy.json 仍需包含它）。
- 停在“等待用户”且等的是命令批准时，由驱动器推进的项目用 wf approve；wf resume 回到评审后驱动器会重新评审并再次停下（会给出提示）。
- 说明类备注（wf note --kind info）出现在回报 ① 段之后的“说明（备注）”中。

## 13. 1.5.2 并发、判据与续传

- 状态并发（W18）：状态的读-改-写在跨进程状态锁（local/locks/<项目>.state.lock）内完成，与磁盘三方合并，只写回本进程改过的字段；事件序号按磁盘上的最新值分配，追加也在锁内。驱动器每一步之前合并一次并检查暂停。
- 判据与熔断（W21）：见第 5 节。探查性的检索（可能无匹配）写判据 exit=1，或改用 sed、cat。
- 续传（W20）：续传先于本轮原文嵌入；一片都放不下时不输出空标题。
- 手工回报（W19）：wf report 生成的本轮草稿由驱动器接着发送。
- 开新对话：先 wf conv new，再发送说明消息（第 3d 节）。

## 14. 1.5.3 Claude 页面快照与对话记录

## 21. 1.6.1 把“需要人”的停顿降到底线本身

用户第 35 轮：“需要执行端做的事”最慢要等一小时，流程因此空转；要求彻底解决。原则不变：任何自动路径都不解除因四道底线而停下的等待，不改动底线，不撤销暂停。在这个范围内，三类停顿改为驱动器自己处理：

- 不扩大权限的白名单与目标变更：版本包改动了 policy.json 或 goals.json，但新白名单没有新增命令或管道过滤、没有去掉停止规则与门禁、没有放宽任何上限、没有新开自动落地或自动安装、没有不认识的键变化；新目标的每条检查命令都在已批准的白名单内——评审不再停下，落地后由驱动器自动批准（approvals.json 与事件里标明 by=driver、“驱动器自动批准（不扩大权限）”）。扩大权限的变更照旧停下等用户。
- 落地前工作区有未经交付的改动（AP-2）：存成一个单独的提交（“wf: 落地前保存工作区里未经交付的改动”），记入回报的偏离与决策日志，再落地。改动里有疑似密钥时不存，照旧停下。
- 每日自动轮次上限：上限不变，达到后不再停下等人，等到第二天（UTC 零点）自动继续。

仍然需要人的：四道底线命中、扩大权限的白名单与目标变更、白名单外的命令、连续验收未通过与目标长期没有进展的熔断、发送结果长时间不明、对话体量达到上限（开新对话，见路线图 1.8.0 的官方 API 通道）。

## 22. 1.6.4 驱动器自己开新对话

collab-wf-dev 第 44 轮，执行端按用户的决策顺位（“交由人工参与的，也交给执行者；执行者没有办法决策和执行的，最终才让人工参与”）决定：对话达到上限时由驱动器开新对话。这一步每 20 轮必然发生、纯属机械，此前是唯一固定需要人的停顿。

- 开启：policy.json 的 auto_new_conversation 为 true。它属于授权：开启按扩大权限处理，需要批准；关闭不需要。通道适配器要实现 conv_new 动作（TRANSPORT.md 附录）。
- 流程：对话达到上限时，驱动器照常生成恢复包（bootstrap 事件记 by=driver），然后：① 选续接消息：开启了同步、并且这次同步已推送或内容没变时用短消息，否则用长消息；② 把本轮原本要发出的消息（通常是回报）原样附在后面；③ 续接消息先通过发送前检查；④ 记下意图，调用适配器 conv_new；⑤ 成功后对话计数归零（conv.by=driver），conv_new 事件记 by=driver，上一轮的 ref 不再交给适配器，本轮回报原件改名为 turn-NNN-report.md 留档，续接消息写入 turn-NNN.md，作为本轮消息照常发送；⑥ 收到回复后照常推进。
- 失败：恢复包没有生成、续接消息没通过检查、conv_new 失败，都不切换，退回原来的做法（CONTEXT_FULL，停下等人），详情写明原因。conv_new 调用超时属于结果不明（可能已经建好），保留意图、不再自动重试，避免重复建对话；之后人工开了新对话（wf conv new）、计数归零，意图自动作废。
- 顺序：交接消息与本轮消息合成一条，等它的回复落地才会发下一条，不会出现“上一条还在生成又发一条”（collab-wf-dev W39）。
- M1：自动开新对话的那一轮没有人工事件，无人值守的连续段可以跨对话。

## 23. 1.6.5 卡死与错误都进 inbox；发送间隔；没落地的重发；执行端代决

collab-wf-dev 用户第 53 轮：“我希望各类驱动器，各类错误，各类需要人工执行的，需要执行器执行的，都发到 inbox……任何一个环节卡死，我希望都有信息到 inbox，并通知你解决。”

- 外部信号：`wf signal add --key <键> --title <标题> [--why …] [--for executor|user] [--ttl 秒]`、`wf signal clear --key <键>`、`wf signal list`。信号存在 local/signals/，由写 inbox 的同一处合并（inbox 里的 key 为 `signal|<键>`），所以独立进程投递的信号不会被下一次 wf tick 冲掉；处理掉后清除，带 --ttl 的到期自动丢弃。
- 看门狗：`wf watchdog [--json] [--write]`，纯只读判定。--write 把每项结果写成 `watchdog:<项目>:<检查>` 信号、恢复后自动清除，并立即重写 inbox（驱动器停了、wf tick 不再运行时也能写进去）。它由独立于驱动器的定时进程调用：驱动器卡死时自己报不出来。阈值：

| 检查 | 判定 |
|---|---|
| driver_stale | 最近一次 wf tick 早于 15 分钟（定时器没有加载或在报错） |
| driver_hung | 驱动器进程还活着，这一次运行超过 25 分钟，且不是在执行命令 |
| exec_overrun | 一条命令超过 command_timeout_s 再加 5 分钟仍未结束 |
| poll_overdue | 等回复时，到了 poll_after 10 分钟还没有轮询 |
| send_unknown | 发送结果不明超过 60 分钟 |
| dwell | 同一步停留过久：等回复 45 分钟、发送 60 分钟、其余步骤 30 分钟（空闲、完成、有到期时间的等待、等用户、阻塞与执行除外：等用户与阻塞本来就在 inbox 里，执行由 exec_overrun 管） |

  连续验收未通过与目标长期没有进展已有熔断，照旧以“阻塞”进 inbox。项目锁是 fcntl 锁，进程退出即释放，不会残留；进程活着却卡住由 driver_hung 覆盖。
- 升级：交给执行端的事在 inbox 里超过 2 小时还在，转给用户（for=user，标题写明）；额度等待本来就会持续数小时，除外。
- 发送间隔（W42）：policy.json 的 min_send_gap_s（默认 0，不改变原有行为；属于时间参数，改动不算扩大权限）。上一条回复落地后不满这个秒数，不发下一条：太早发送会接到上一条残留的生成，被误判为已接受。
- 没落地的重发（W43）：SEND_NOT_LANDED 阻塞时，`wf resend --code <决定码>` 恢复本轮消息为待发、清掉旧 ref，由驱动器重新发送；不要用 wf unblock --to WAIT_REPLY（会一直等一条不存在的回复）。
- 执行端代决（W43，用户第 44 轮的决策顺位）：approve、unblock、resend、policy approve、goals approve 可以用 `--by executor --reason <理由>` 代替 `--said`，事件如实记 by=executor（M1 算作人工动作）。只限 inbox 里交给执行端的事项；四道底线、撤销暂停、目标达成仍只认用户原话（--said），执行端代决会被拒绝。
- wf explain 的“需要”与 inbox 的路由一致：交给执行端的事项显示“执行端”。

## 24. 1.6.6 执行端待办：写给执行端的事可以追踪

collab-wf-dev 第 58 轮：回复正文里写给执行端的事，执行端做完了却没有接上回报（要记得 wf kick），流程停在空闲；服务都健康，看门狗也看不见，业务却停了。

- 写法：【驱动指令】里每件事一行“执行端 N：<事项>”。“之后”可以写“等执行端”：等这些事做完再回报。
- 登记：驱动器验收后把它们登记为 T<轮次>-<序号>，每一项都进 inbox（key 为 task:<编号>，交给执行端，超过 2 小时转给用户）。`wf task` 列出全部待办。
- 完成：执行端做完一项就 `wf task done <编号> --note "结果"`。结果作为说明写进回报；事件记 by=executor（这是执行端的动作，M1 照实计入）。
- 接续：“之后：等执行端”或“之后：空闲”而又有未完成的待办时，驱动器停在等待（WAIT_SCHEDULE，原因“执行端待办”），全部做完就自动生成回报并发出，不再需要 wf kick。到了最迟时间（policy.json 的 executor_task_timeout_s，默认 4 小时，时间参数）仍有没做完的，也照常回报，并在“偏离”里列出没做完的待办。
- “之后：回报”时待办照样登记、照样进 inbox，回报照常发出；之后做完的结果随下一份回报带上。
- Claude 写给执行端的事，一律写成“执行端 N：”，不再只写在正文里（此前的“给执行端：”段落没有可追踪的出口）。
- 1.6.7：目标已达成时同样登记（collab-wf-dev 第 80、81 轮：此前目标判定在前，达成即进入 DONE，待办被静默丢弃）。DONE 的语义不变：自动化停下等用户，“之后”不起作用，不等待、不自动回报、不推进版本；待办照样进 inbox 交给执行端，`wf explain` 先说待办。做完后 `wf task done` 写明不会自动回报，结果写进 inbox 的“目标已达成”提示（key 仍是 done:<轮次>）；需要交给 Claude 时 `wf kick`。

## 25. 1.6.8 失败不被 DONE 吞掉；落地核对按墙钟；R3 飞行宽限；审查演练

collab-wf-dev 第 82、83 轮与改进批次一（P1-D、P2-E）。

- 目标判据通过、但本轮有验收未通过或命令失败时，不进入 DONE，照常回报（决策日志写明“先回报，不进入目标达成”）。DONE 只在“目标达成且本轮干净”时进入；下一轮干净、目标仍达成，照常进入 DONE。执行端待办照样先登记（1.6.7），熔断照常计数。
- 落地核对（SEND_NOT_LANDED）：policy.json 新增 `landed_timeout_s`（秒）与 `landed_min_polls`（默认 3），都是时间参数，改动不算扩大权限。设了 `landed_timeout_s` 时按墙钟：距本轮发送（sent_at）已满这个秒数、且至少核对了 `landed_min_polls` 次才停下；此时 `landed_confirm_polls` 不再起作用，`landed_poll_s` 仍是核对间隔。没设时沿用旧的次数判定（兼容）。迁移：在 policy.json 里加 `"landed_timeout_s": 2700`，旧的两个参数可以保留。不变量不变：SEND_NOT_LANDED 不自动重发，恢复只用 `wf resend`。
- `wf bridge-check` 的 R3：发送之后还没有结果、也还没有新的发送时，距现在不超过宽限（`--grace-s`，默认 900 秒）视为仍在飞行、不报，消息里写明在等待；超过宽限照常报（此前作为最后一条的发送永远不报）。结果出现之前又有新的发送，一律报。`--hours` 只过滤日志窗口，不是宽限。
- `wf drill review --kind block|timeout --dir <空目录> --review <审查程序>`：在隔离目录里让真实驱动器消费真实审查程序的 block 与超时，见 docs/DRILL.md。

## 26. 1.6.9 加固：可见的等待、少报误报

collab-wf-dev 第 86–88 轮（执行端加固需求甲）。

- 审查等待可见（P0-A）：自动安装前等独立审查时，wf self-update 先输出“开始等独立审查（上限 N 秒）”，之后每 `review_heartbeat_s`（transport.json，默认 30）秒输出“仍在等独立审查：已 X 秒 / 上限 N 秒”；没有结论时输出“本次未审查：原因”，并写 local/reviews/<版本包名去掉 .zip>.unreviewed.json（例如 collab-wf-1.6.9.unreviewed.json；时刻、原因、diff 路径），版本照常安装，事后可按 diff 补审。运行新版本自检前也先输出一行。“未审查不阻止安装、只有 block 能阻止”不变。
- 执行端不在场时（P0-B）：在场检测属于执行端的审查程序（它知道有没有可用会话）。约定：没有可用会话时，审查程序应在几秒内以非 0 退出（例如输出 `{"verdict": "unreviewed", "reason": "no_session"}`），工具按“未审查”继续；有会话时才等，等待上限仍是 review_timeout_s。不采用“先安装、事后 block 再回滚”：回滚是护栏命令（self-rollback），驱动器没有调用它的路径，而且未审查的代码会先跑起来。
- 发送结果不明（N8）：SEND 有待定的发送意图（结果不明、SEND_UNKNOWN_WAIT 正在反复确认）时，停留上限按 65 分钟计，不再在 15 分钟时误报“停留超过上限”；看门狗的 send_unknown（60 分钟）不变。
- 暂停与静音（N9）：已暂停的项目、wf.json auto=false 的项目，不再出现“停留超过上限”提示，看门狗不报停滞，驱动器心跳不判“停了”；wf schedule status 把 auto=false 的项目标为“已静音”，不计入“定时器可能没有运行”。暂停本身仍在 inbox 里交给用户。
- 同步暂停提示（N6、N7）：标题按实际命中写（疑似密钥／版本包不是有效的 zip）；key 由命中内容算出，同一原因不再每次 tick 生成新键、反复唤醒。
- 手工开新对话（N10）：wf conv new 清掉上一轮的 send_ref 与 resend_parent，与驱动器自动开新对话一致；否则新对话首轮的轮询会去查旧对话，消息已落地也确认不到，最后阻塞，而 wf resend 会重复发送。
- 不在本版：单条命令受 tick 剩余预算约束（P0-C）随多项目隔离的调度改造一起做（长命令改为后台执行、下一次 tick 收结果），不在半途杀掉 self-update；唤醒投递的自愈（P0-D）属于执行端的唤醒程序；执行端解除自己发起的暂停（P1-A）等用户本人决定后再做。

| 门 | 人不在场时 |

## 29. 1.7.2 每个项目自己的定时任务（多项目隔离 S3）

collab-wf-dev 第 92 轮；设计见该项目的 ISOLATION.md 第 6 节。一次唤醒串行推进全部项目时，一个项目的长命令会占满整次 tick（第 86 轮 912 秒），别的项目都停着。

- `wf --project <名> schedule plist [--interval 60 --max-seconds 540]`：生成这个项目自己的 launchd 配置（标签 `local.collab-wf.tick.<名>`，运行 `wf --project <名> tick`，日志 `local/tick-<名>.log`），并登记在 local/schedule.json 的 projects 里。登记后全局定时任务不再推进它，所以生成后要立即加载；没加载时 15 分钟后心跳报停。
- `wf --project <名> tick`：只推进这一个项目。不带 --project 的 `wf tick` 跳过已登记的项目（回报里写“有自己的定时任务”），其余照旧。
- inbox 每次仍汇总全部项目，并在文件锁里读改写：只写本项目会把别的项目的待办冲掉，而执行端以“key 从 inbox 消失”判定做完。
- `wf --project <名> schedule release`：撤回登记，全局定时任务下次起推进它（另需 launchctl bootout 卸载那个配置）。
- `wf schedule status`：有自己定时任务的项目按它自己的周期判断是否停了。
- 同一项目不会被两个进程同时推进（项目锁不变）。P0-C（单条长命令占满 tick）因此只影响这个项目自己。

## 30. 1.7.3 按项目寻址（多项目隔离 S2 的工具侧）

## 32. 1.7.5 执行端解除它自己发起的暂停（P1-A）

## 33. 1.7.6 不再空转的续接、执行端的补充说明、按项目分仓库

## 34. 1.8.2 交接与目标的硬门

collab-wf-dev 第 104–105 轮（用户的硬要求：每次失败都要变成机制，不靠下次记得）。本版只加不删；floor.py 与四道底线不变。

- 回复完整性（P0-F 的工具侧）：适配器在 poll 完成时给出的 stop_reason、completion_state 写进 evidence/turn-NNN/reply_meta.json（TRANSPORT.md 附录 1.8.2）。continuation_required 且固定块齐全：照常解析与执行，记一条偏离，并在下一条消息末尾请 Claude 先从断点补齐——只在同一个对话里，连续 3 次后不再自动附，改为提示缩小每轮范围。固定块不全：照旧走续接，续接消息写明上一轮的结束原因。
- 暂存目录安全（1.8.0 独立审查 block 后修）：清单路径必须是相对路径、不含 . 与 ..；暂存目录及其到 local/sync 的上级不能是符号链接；暂存目录里的链接只删链接本身、从不跟随写入；写文件一律在同目录建新 inode 的临时文件、写完落盘后原子替换（1.8.1 审查 block：O_TRUNC 会写穿指向外部的硬链接）；写失败时旧文件不变。残余风险：前提是单写者，检查与替换之间若有另一个同权限进程改暂存目录，不承诺防住。
- 命令之间重读暂停，停线边界：每条命令启动前，在状态锁内与磁盘合并两次（取下一条前、登记“执行到第几条”后）并检查暂停；暂停在下一条命令启动前生效。已经开始的命令不中断；第二次检查与子进程启动之间仍有一个不读状态的短窗口，落在窗口里的暂停从再下一条起生效。
- 本机行为探针：`wf self-check --probes` 在临时 local/ 里对已安装的代码跑上面九组检查，逐项输出“探针 名称：通过/未通过”，不碰本机状态。它是只读命令，可以作为阶段目标的机器判据。
- 不在本版：回复发现延迟（发送确认退避上限、done 之后重复轮询、快照长等待持锁；执行端第 105 轮报告，下一版）；执行端同步程序的 --repo、忙时返回非 0、按项目的缓存、锁与日志（执行端范围）；S4 共享仲裁；经验闭环检查器；默认门禁基线。
