方案要点：

1. 形态：一个巡查脚本，放在工具目录之外（例如 ~/.workbuddy-ai/adapter/patrol/），由 Claude 交付；配一个独立的 launchd 任务，周期 180 秒，不改全局 tick 的间隔；配置文件 patrol.json 绑定 main、repair、live 三个会话 id 和项目名。脚本只通过官方 CLI 的 resume 入口和宿主自己的认证投递，不读任何凭据、cookie 或环境密钥，也不运行 wf tick。

2. 每次运行的顺序：
   - 先拿非阻塞文件锁，锁被占用就记“跳过”后退出（互斥）。
   - 读暂停门：用户暂停、项目暂停或 patrol.pause 任一存在，就一次都不投递。
   - 逐个会话核验绑定与活跃证据：会话不存在或 id 对不上，停下并告警。会话正在做时不投递。
   - 只对空闲会话、且有未完成事项时投递；同一事项在得到结束证据之前只投递一次（去重）。

3. 状态只向前推进，每一步有各自的证据：
   - 排队：写入了事项。
   - 送达：CLI 返回成功，且该会话记录里出现了这条投递。
   - 执行：投递之后该会话有开始活动的 hook 记录。
   - 完成：投递之后有 Stop 记录。
   - 验收：事项自己的判据成立。

   runId、PID、“已读”标记都不算消费。

4. repair 先于 main：修复事项先交给 repair 会话，验收成立后才把交接投给 main；main 不接收未经验收的修复。

5. 验收谓词（实景、机检，按审计日志判定）：
   - 三个 id 每次运行都核对一致；
   - 相邻两次运行间隔在 170–240 秒；
   - 运行之间不重叠，同一会话的一个活动期内最多投递一次；
   - 同一事项在完成之前不重复投递；
   - 暂停期间投递次数为 0；
   - main 收到的交接，都对应一个已验收的 repair 事项；
   - 每个事项的状态都有带时刻的证据；
   - 代码里不出现读取凭据的路径，自检用 grep 加以证明。

6. 回滚：放上 patrol.pause 即刻停止投递；卸载这个 launchd 任务，撤掉 hook 配置里新增的条目；审计日志保留。不涉及工具目录。

7. 未完成项与可能的阻塞：
   - 官方 CLI 能否对一个已存在的会话追加消息、能否在图形界面打开时安全地 resume、并发 resume 会怎样；
   - hook 能否按项目配置，以及能否防止我们自己的投递触发递归；
   - “正在做”有没有可读的证据。

   其中任何一项平台不支持，我都会如实写成阻塞，不用 watchdog 或心跳去冒充。
