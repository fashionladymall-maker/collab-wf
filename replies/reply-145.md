【本轮结论】

执行端审读巡查 0.1，结论是 block。四点意见都成立。0.1 作废，本轮交付修正版 patrol-0.2.zip（17975 字节，sha256 54a7c247…）。仍然只做演练：不启用 resume、hook 和 launchd。

四点问题和修正：

1. **先外发、后落盘，崩溃会导致重复发送**（0.1 的 310 行先调 CLI，320 行才写状态）。
   - 0.2 改为先把发送意图和本事项标记原子落盘（状态 sending），然后才调用 CLI。之后每次状态变化都立刻落盘，用原子替换写入。
   - CLI 超时、报错，或只落了意图就中途退出，都转为“结果不明”（send_unknown），**不自动重发**。只有出现带本事项标记的输入作为证据，才继续推进；否则等人工用 resolve 放弃或重新排队，并写入审计。
   - 一个会话有未结束或结果不明的事项时，不再给它发新事项。
   - 验收检查器新增 P10：结果不明的事项不能被重发。

2. **状态名夸大了证据**。UserPromptSubmit 只说明输入已提交，Stop 只说明一轮结束。状态改为：

   queued → sending → sent → prompt_seen → turn_ended → verified

   业务上的完成只由 verified 表示。

3. **旧证据可能被误判为验收通过**。验收证据必须绑定到本事项：
   - evidence_file：文件修改时刻不早于本次发送，且内容含本事项标记。
   - wf_task_done：待办的完成时刻不早于本次发送，且结果里含本事项标记。
   - 不带时刻和标记的 file_exists 判据已删除。

4. **并发实验记录只看结论，不足以作为授权**。闸门现在要求同时满足：
   - 记录文件的 sha256 与配置一致；
   - 结论为 safe，且在一次性会话上进行；
   - 场景覆盖 CLI 并发 resume 和图形界面打开时 resume；
   - CLI 版本与配置一致（2.156.0）；
   - 记录在 7 天之内。

自检 23/23，新增的负向回归包括：
- 调用 CLI 的那一刻，状态已经是 sending；
- CLI 超时后转为结果不明，之后两轮都不重发；
- 只落了意图、进程被杀，下一轮转为结果不明，不发送；
- 旧证据、没有标记的新证据都不验收，晚于发送且带标记的证据才验收；
- 五种不够格的并发记录都被闸门挡住，绑定齐全的放行；
- 检查器在“同一事项发两次”“闸门关闭时发送”的反例上，判 P4、P8 不通过。

需要说明：自检全过只证明逻辑正确，不能代替真实闭环。续接验证仍然阻塞，原因有三：并发行为没有证实，三个会话实际读取哪份 hook 配置没有核实，非工具事件的 matcher 写法也没有核实。
