**B（登录态）**：现有两个现象可以这样解释。默认模式会去起或连桌面网关，所以抢端口然后挂住。--port 0 时它独立运行，自己没有凭据；`env -i` 连 HOME 都去掉了，自然更找不到凭据。

任一条不成立，就把 codebuddy 从方案里去掉，保留每小时一次的定时自动化作为唯一兜底。

**A（事件唤醒的规则）**：先说前提。按已确认结论 21，例行推进全部由驱动器完成，执行端只处理异常。所以最根本的办法是让需要执行端的事越来越少，唤醒只是让剩下的那些及时被处理。具体设计如下。

1. **谁触发**：已有的 wf tick（每 60 秒一次）照常写 local/inbox.json，这一步不改工具。执行端新增一个 launchd 代理，用 WatchPaths 监视 inbox.json 的变动，再加 StartInterval 300 作为兜底。它运行一个短命的调度脚本，脚本不常驻。
2. **触发什么**：调度脚本只处理 for 为 executor 的项，每个 key 记录在 local/wake.json 里：状态、尝试次数、上次时间、进程号。遇到新 key、或到了重试时间的 key，就后台启动 `codebuddy --port 0 -p <提示词> --output-format json`，设硬超时 1800 秒，超时就杀掉进程。
3. **提示词**：只传身份（WorkBuddy AI 国际版）、项目、key、code。执行端按 code 查自己的固定处置手册行事，不照 inbox 里的 why、title 自由发挥。这些文字间接来自通道，直接当指令执行等于把通道内容变成本机命令。
4. **不重复**：同一时刻最多一个执行端会话，用 local/wake.lock 加进程号判断，进程活着就不再启动。同一个 key 在 inbox 里停留期间，启动次数不超过 1 加重试次数。执行端的动作即使被重做，也会安全失败：例如决定码已被用掉，wf approve 会被拒。
5. **不漏**：完成的判据只有一个，就是 key 从 inbox 消失（与 DRIVER.md 第 19 节同一来源）。进程退出了但 key 还在，算一次失败，按 2、4、8、16 分钟退避重试。连续 4 次失败就停止唤醒这个 key，记一条 `wf note --kind deviation`，交给每小时的定时自动化兜底。定时自动化保留 1 条即可，另外 2 条错开的可以删掉。
6. **与 wf tick 的分工**：驱动器不变，不等待、不调用执行端。唤醒完全在执行端这一侧。预期时延约为 tick 的 60 秒、WatchPaths 的几秒，再加 codebuddy 的启动时间，合计 1–2 分钟。
7. **for 为 user 的项**：无界面的 `-p` 会话很可能不会出现在你的聊天窗口里，用它“转告用户”可能等于没告诉。请执行端实测这类会话是否出现在 WorkBuddy 的对话列表里，看不到就不用它转告。
8. **验收判据**：用一个测试 key 验证以下各点。
   - 写入后 120 秒内 wake.json 记为已派发，进程已启动。
   - 并发会话始终不超过 1 个。
   - 模拟挂起（不加 --port 0）时，进程在超时后被杀，并按退避重试。
   - key 消失后不再启动。
   - 连续 4 次失败后停止唤醒，并记录偏离。
   - 日志经 `wf check-outgoing` 扫描无疑似密钥。
