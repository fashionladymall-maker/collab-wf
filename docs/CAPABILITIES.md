# CAPABILITIES.md —— 能力边界、操作边界与失败模式（collab-wf，对所有项目通用）

目的：让用户知道每一方能做什么、不能做什么、可能在哪里出错，以及怎样核对"没有出错"。原则是信任靠可核对的证据，不靠任何一方的自述。

## 1. Claude（网页对话中的设计与编码方）

**能做**：设计方案；编写全部代码；在自己的隔离 Linux 容器里运行代码做测试（只能连 pypi、npm、GitHub 等少数站点；2026-10-10 实测：可以克隆 GitHub 公开仓库，私有仓库需要凭据因而不可用，GitLab 与 Gitee 不可达）；生成并交付文件；解读执行端回报的结果；维护 PROJECT.md 与 CHANGELOG.md。

**做不到**：
- 访问用户的电脑、交易所（币安的任何域名在 Claude 的容器里都不可达）或执行端的环境；只能看到执行端回报的内容。
- 用真实行情测试代码：交付前的测试都用模拟数据或伪交易所完成，真实数据上的表现只能由执行端验证。
- 常驻运行或主动发起对话：只在收到消息时工作。
- 保证容器文件跨轮保留：容器可能重置，权威副本在本机 git 仓库。
- 选择或看到自己的档位与模型、观察通道内部状态（例如发送被拒的原因）、核实执行端对通道的描述。

**不会做**：经手 API 密钥；替用户下单、开户、转账；帮助绕过交易所地域限制；设计轮换共享账户以绕过用量限制的机制；编写或审读调用第三方站点内部接口、操作用户浏览器会话的代码。执行端的传输适配器由 Claude 定义接口与行为约定，并用黑盒一致性检查与动作日志核对（DESIGN.md 第 2 节）。

**容易出错的地方**：
- 代码缺陷：已用模拟数据测试，但真实环境的边界情况（网络抖动、交易所规则、数据缺口）可能没覆盖到。由执行端的实测与 reconcile.py 对账兜底。
- 统计判断：样本有限时结论不稳。PROJECT.md 中标注了每个关键数字的不确定性（标准误）。
- 同一轮的多次生成：安全防护拦截后续写、或重新生成时，同一轮会有多次生成，它们共用同一个代码容器，可能各自写文件、各自交付。Claude 在某一次生成里看到的文件，可能来自同一轮更早的一次尝试；交付以最后一条完整回复为准（AUDIT.md 第 1 节）。
- 平台差异：Claude 在 Linux（bash 5、Python 3.12）上测试，执行端在 macOS（自带 bash 3.2、Python 3.13）上运行。shell 脚本在两者之间行为可能不同（已遇到：中文字节被并入变量名、EXIT trap 改写退出码），这类问题只能由执行端实测发现。Claude 写脚本时按 bash 3.2 的保守写法：变量加花括号、不依赖 bash 4 以上的特性、trap 保留原退出码。
- 知识时效：对交易所规则、产品功能的了解可能过时，涉及这些时应以官方文档为准。
- 引用与事实：Claude 可能记错外部信息，涉及外部事实的结论需要核对来源。

## 2. 执行端（WorkBuddy AI，运行在用户 Mac 上）

以下依据执行端的自述，Claude 无法独立核实。

**能做**：读写本机文件；运行 Python 与 Node；在虚拟环境中安装包；运行长时间后台任务；启动本地网页服务；通过第三方站点收发与 Claude 的消息、下载交付文件、查询额度。

**做不到**：控制用户正在使用的 Chrome（系统沙箱拒绝）；访问 api.binance.com、api.binance.us、fapi.binance.com；访问 claude.ai 或 Anthropic 官方 API；常驻运行（只在用户发消息时被唤醒）。

**不应该做**：替用户做资金、密钥、合规决定；擅自修改业务代码；把转述当作原文回报。

## 3. collab-wf 工具本身的边界

- 只在本机运行，不访问任何网络，也不访问通道。通道步骤的状态依赖桥接工具在接入点调用 wf；如果漏调用，状态会落后于事实。wf status 与看板显示的是"记录到的事实"，wf doctor 能发现步骤超时，但不能发现所有遗漏。
- 命令风险分级与密钥扫描基于规则匹配，会有漏报和误报。它们是提醒与拦截的第一道关，不是安全边界：密钥从一开始就不应该出现在任何消息里。
- wf 不判断 Claude 的回复是否真正解决了问题，验收结论由执行端逐项给出。
- 计划节点到期不会主动通知任何人：执行端被唤醒时 wf status 会提示，看板会把逾期标红。
- 工具在 Claude 的 Linux 环境中通过了端到端自检；在 macOS 上以本机运行 wf selftest 的结果为准。
- 驱动器会自动执行回复中的命令。能控制通道的人（包括第三方站点的运营方）理论上可以借此在本机执行命令。防线是：白名单默认拒绝、内置停止底线、护栏命令只能由用户执行、命令拼接需要批准、版本包新增内容检查、熔断与每日上限。白名单越宽，这道防线越弱。
- 批准记录（approvals.json）能阻止驱动器自行越界，但无法在技术上区分用户本人与同一台电脑上的其他程序；它是有记录、可审计的动作，不是签名。
- 决定码（1.4.0）把一次批准绑定到一件具体的待决事项上，防止含糊的“好的”或过期的批准落到错误的事项上。它同样不能防止执行端伪造用户原话；防线是原话被逐字记录在事件流与决策日志里，用户可以在看板上核对。
- 门禁的强度取决于门禁本身：项目没有行为测试时，门禁只能发现导入与语法这一级的回归。
- 驱动器相信传输适配器的报告。适配器误报（例如把“看不到”报成“完成”）会让驱动器做出错误的推进；适配器必须遵守 TRANSPORT.md，并用 wf bridge-check 定期核对其日志。

## 4. 通道（第三方站点 c.aimonkey.plus）

这不是 Anthropic 的站点，账户为共享或转售账户（"车队"）。由此带来的风险：
- 隐私：站点运营方技术上可以看到全部对话内容，包括策略与代码。因此任何密钥都不能经过这个通道。
- 可用性：共享账户不符合 Anthropic 服务条款，可能随时被停用，对话可能丢失。本地 git 仓库与 PROJECT.md 是对冲这一风险的手段。
- 限制与行为：额度规则、接口行为由该站点与账户决定，可能随时变化；执行端已观察到发送被拒和消息延迟落库（见 PROJECT.md 失败模式台账 F04、F05）。

是否继续使用这个通道，由用户本人决定。

## 5. 只有用户能做的事

决定交易平台与所在地是否合规；创建与保管 API 密钥（只存放在本机 .env）；决定投入资金和是否上实盘；决定使用什么通道与 Claude 协作；接受或否决策略定位。

## 6. 通用失败模式与应对

| 失败模式 | 怎样发现 | 谁处理 | 应对 |
|---|---|---|---|
| 执行端误解指令或执行偏离 | 回报 ① 段；与【本机执行】逐条比对 | Claude | 在【本轮结论】中指出并给出修正指令 |
| Claude 代码缺陷 | 本机报错；reconcile.py 不一致；结果明显异常 | Claude | 定位修复、发布新版本、补充测试 |
| Claude 解读错误 | 执行端或用户质疑；与原文数字不符 | Claude | 回报中附原文，便于双方核对 |
| 结论过拟合 | 样本外与样本内差距大；参数邻域不稳 | Claude | 判定标准事先写死；用滚动前推与邻域检验 |
| 上下文丢失（新对话） | Claude 复述与 PROJECT.md 不符 | 执行端 | wf bootstrap，按 WORKFLOW.md 第 10 节恢复 |
| 版本混乱 | wf apply 校验失败；git 历史缺口 | 执行端 | 只通过 wf apply 落地版本；需要时 wf rollback |
| 额度用尽 | 通道返回额度错误（退出码 3） | 驱动器；预算耗尽时由用户处理 | 有界等待后回到原步骤。发送被拒的消息（按适配器契约视为未接受）等待后再发；等回复时保留原对话与 ref，继续核对原回复，不重发。默认一次恢复期最长 8 天、最多 12 次试探，耗尽或记录损坏时阻塞。驱动器不自动切换账户或资源；经授权的人工切换照 WORKFLOW 第 10 节交接 |
| 回复中断 | 回复缺少固定块，或因工具调用、长度上限结束 | 驱动器；超过续接上限时由用户处理 | 请 Claude 从断点继续，不整条重发。同一轮同一种情况第 3 次出现，或连续 3 轮续接仍缺块时阻塞 |
| 发送结果不明，或已接受但登记未完成 | 适配器超时、只收到心跳；或重启后发现本轮已被接受但登记没走完 | 驱动器 | 保留发送意图，只轮询核对：不重发、不取新租约。缺 ref 时，只凭本轮持久证据（意图或 last_sent 与外发正文副本）按时刻与正文定位，否则停下（NO_REF，再次出现即阻塞）。结果不明的等待默认约 1 小时（扣除读不了通道的时段），并受恢复期硬截止约束，仍不明则阻塞 |
| 发送被拒 | 通道返回错误 | 执行端 | 按 SEND 步骤的异常表处置（wf step SEND） |
| 长期运行的进程中断 | 看板项目进程条变红；wf doctor 报告未运行 | 执行端，用户配合 | 查电脑睡眠、断网；按 wf.json 中声明的 start 命令恢复 |
| 脚本修复了自身，但验证时跑的仍是旧版本 | 修复后首次运行仍报旧错误 | 执行端 | 以新版本实际执行的那次为准；工具升级用 wf self-update，先自检后安装 |
| 失败被静默成成功（退出码为 0 但实际出错） | stderr 有报错但退出码为 0 | 执行端发现，Claude 修复 | 回报同时给出退出码和 stderr；脚本 trap 必须保留原退出码 |
| 工作流状态与事实不一致 | 看板显示的步骤与实际不符；wf doctor 报告超时 | 执行端 | wf force 更正（会被标记）；检查桥接工具的接入点是否漏调用 |
| 自动执行越过边界 | 评审停在等待用户决定；审计中出现白名单外的执行 | 用户 | 白名单默认拒绝 + 内置底线 + 护栏命令；wf audit 复查；必要时 wf undo |
| 驱动器反复失败或空转 | 熔断：连续未通过、目标无进展、每日轮次上限 | 用户 | 查看本轮证据后 wf approve 继续，或 wf pause 接管 |
| 驱动器运行中被打断（睡眠、重启） | 看板显示上一次驱动未正常结束 | 驱动器 | 从落盘的意图接续：不重发、不重跑，结果不明时安全停机 |
| 外部数据源变化或不可达 | 下载报错 | 执行端回报，Claude 修复 | 记入失败模式台账 |
| 密钥泄露 | 密钥出现在任何聊天、日志或 git 中 | 用户 | 立即在交易所作废并重建；.env 已被 git 与看板屏蔽 |

## 7. 怎样核对"没有出错"

- 每个结论都能追到原始文件：results/ 中的报告、logs/ 中的流水账、git 中的代码版本。
- 关键判定的标准在结果出来之前写入代码。
- 工作流的每一次状态转换、执行、验收都记录在 events.jsonl 中，人工更正会被单独标记。
- 项目自己的对账或测试（例如 btc-quant 的每周对账）按项目约定执行，结论写入回报。
- PROJECT.md 结构由 wf 校验，版本号与 CHANGELOG.md 必须一致；校验不通过的版本不会被落地。
- 看板只读取本地文件，显示的是事实而不是任何一方的转述。
