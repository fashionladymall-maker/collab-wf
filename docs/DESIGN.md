# DESIGN.md —— collab-wf 完整设计（1.2.0）

本文件是整套工具的总设计：从用户在对话窗口说的第一句话起的全部诉求，到每条诉求由什么机制满足、做到了哪一步、哪些不做以及为什么。具体用法见 USAGE.md，驱动器细节见 DRIVER.md，适配器约定见 TRANSPORT.md，能力边界见 CAPABILITIES.md。

## 1. 目标与边界

**一句话目标**：用户给出目标和完成判据，并批准自动化的权限范围；之后由工具驱动“Claude 设计与编码 → 本机落地、执行、验证 → 回报 → 下一轮”的循环，直到判据通过；只有四类事和真正的异常才停下来问用户。

**用户已拍板的三条**：自动跑完整轮，只在资金、密钥、合规、上实盘以及异常时停下；完成由可执行判据决定，判据须经用户批准；靠系统定时唤醒，不要求常驻进程。

**红线（写在代码里，项目无法关闭）**：资金、密钥、合规、实盘四类命令；版本包中新增的实盘开关、密钥赋值、提现转账调用；修改自动化自身护栏的命令。

**不做的事**：
- 不轮换共享账户（“换车队”）来绕过用量限制。额度用尽的标准动作是等待重置。开新对话的恢复包照常提供，它对任何正当的新对话都有用。
- Claude 不编写、不审读调用第三方站点内部接口或操作用户浏览器会话的代码。这部分由执行端实现，Claude 定义接口并负责黑盒验证（第 2 节）。
- 不引入远程仓库：私有仓库需要经聊天传递凭据，公开仓库会公开策略代码。上下文靠本地 git、仓库指纹、按需文件包和恢复包。

## 2. 角色与所有权

| 参与者 | 负责 | 不负责 |
|---|---|---|
| 用户 | 目标与判据、白名单、四类红线决定、通道选择、暂停／回退／接管 | 例行操作 |
| Claude | 全部设计；collab-wf 与项目的全部代码；适配器接口与一致性检查；审计与复盘规则 | 通道内部实现 |
| 驱动器（wf） | 按状态推进、记账、取证、判定、回退、停下并说明原因 | 写代码、做决定之外的判断 |
| 执行端 | 传输适配器的实现（发送、轮询、额度、可选的独立审查）；系统定时器；验收回报中的意见 | 方案、业务代码 |

关于执行端工具的审计（需求 3.11）：这部分的架构由 Claude 负责到接口为止。接口与行为约定见 TRANSPORT.md；正确性用三种方式核对，而不是靠阅读通道代码：
1. `wf transport test`：黑盒一致性检查（不发送消息），检查轮询语义、幂等、额度格式和动作日志；
2. `wf bridge-check`：按六条行为约定核对适配器的动作日志；
3. 驱动器在运行中只相信符合约定的输出，任何不符合约定的输出都按异常字典安全停机。

如果将来改用受支持的通道（例如官方 API），Claude 可以直接编写该通道的适配器。执行端自建代码的逐份审计结论见 AUDIT.md。

## 4. pstack 研究

落地成可照做的流程见 PROCESS.md（1.5.5）：每一条写明做什么、为什么、谁做、怎样算做到了。

**它是什么**：pstack 是 Cursor 官方插件 `cursor/plugins/pstack`（作者 poteto）的技能包，`backnotprop/pstack` 是它面向其他代理工具的镜像。内容是 24 项工程原则、27 项技能、23 个任务 playbook，均为纯文本的 Agent Skills。入口 `/poteto-mode` 把任务匹配到 playbook，把 playbook 的步骤原样抄进待办，再按步骤调用其他技能。

**它的闭环**（源码：playbooks/autonomous-run.md、docs/guide/07-overnight.md）：先把“完成”写成可检查的谓词；用 `/loop` 心跳或事件唤醒；每轮做证据支持的最小改动，在真实产物上验证，推进了就提交、没推进就丢弃；每轮记一行决策；谓词满足才停，平台期要换思路，绝不放宽谓词；“时长不是完成条件”。

**多模型的做法**：按角色分配模型与推理预算（`/setup-pstack`，预算 unlimited / large / medium / small 对应 max / xhigh / high / medium）；默认代码交给 Grok、判断与最难的改动交给 Opus 5.5；`/interrogate` 让多个模型用同一提示审同一份 diff，一致的发现信号最强，结论不自动应用；`/show-me-your-work` 用另一个模型系列审查决策记录，回复末尾给出“Attention”。

**无人合并的做法**（playbooks/autopilot-full.md、shipping.md）：任何负责人都不能凭自己的结论合并；必须由没写这段代码的验证者在确切的提交上给出干净结论，其中“在真实界面上运行”的验证是底线；结论只对确切的补丁有效（patch-id 规则）；“CI 绿了”不等于结论；运营者的全自主授权加上独立的干净结论，才构成合并授权。不可逆操作始终需要人。

**对照我们的条件**（网页版 Claude 没有子代理、执行端不常驻、通道有额度）：

| pstack 做法 | 我们的处理 | 实现 |
|---|---|---|
| 完成写成可检查的谓词，不放宽 | 直接采用：goals.json，批准后按内容哈希锁定，改动即失效 | 1.1 |
| /loop 心跳唤醒 | 直接采用：系统定时器运行 wf tick（没有事件源，只用心跳） | 1.1 |
| 推进就提交，没推进就丢弃 | 改造：门禁在落地前后各跑一次，落地后回归就自动回退 | 1.2 |
| 决策日志 decisions.tsv | 直接采用：decisions.jsonl，可导出 TSV；回报末尾的“需要注意” | 1.2 |
| 另一个模型系列审查 | 改造：可选的独立审查适配器，由执行端接入任意其他模型；只能阻止或提醒，不能放行 | 1.2 |
| 按角色分配模型与推理预算 | 改造：同一模型的档位按角色分配，预算统一调节；每轮记录与复盘 | 1.2 |
| 负责人不能凭自己的结论合并 | 改造：门禁由用户批准并锁定，Claude 的版本无法单方面放宽；回归自动回退 | 1.2 |
| 结论只对确切补丁有效 | 改造：批准按内容哈希；仓库指纹 | 1.0–1.1 |
| 协调者从不写代码 | 直接采用：驱动器只落地 Claude 的版本，不改任何代码 | 1.1 |
| 有限重试、终止交接、卡住判断看副作用 | 直接采用：异常字典的次数上限；停下时写清原因与下一步；看板按驱动器心跳判断定时器是否停了 | 1.1–1.2 |

## 4a. 交互形态（1.4）

用户在 WorkBuddy 聊天窗口里说话，执行端翻译成 wf 命令；需要用户决定的事由执行端主动呈报到聊天窗口；执行端不在场时，看板是用户的信息来源。看板保持只读：它运行在本机端口上，一次点击无法证明是用户本人点的，而聊天天然留下用户原话。用户要“能点的东西”时，由 WorkBuddy 把呈报中的回复选项做成快捷回复，点击等于发送那句话。

每件待决事项有一个由内容算出的决定码，批准必须带码与用户原话，码不对或事项已变就拒绝。用户需要会说的只有六句话（USER.md）；看进度、健康检查、开新对话都是执行端自己的活。

不做的：看板写操作、移动端、多用户、推送通知。

## 5. 一轮的完整运行

```
定时唤醒 → 加锁 → 健康检查（声明的进程掉线就按白名单拉起）
→ 组织消息（节点、续接、回报；档位按角色规则；密钥扫描；对话体量检查；全局限速）
→ 发送（先落盘意图；被拒退避；额度用尽等待重置）
→ 等待 Claude（定时轮询；看不到不等于丢失）
→ 接收与解析（五个固定块与【驱动指令】；缺块请求续接）
→ 执行前评审（白名单、红线、拼接、版本号、版本包新增内容、可选独立审查）
→ 落地（门禁基线 → 落地 → 门禁复查；回归则自动回退并回报）
→ 执行与取证（逐条落盘进度；被打断不重跑）
→ 验收（按判据逐项；目标检查；熔断；按【驱动指令】回报、等待或空闲）
→ 记账（事件、决策、轮次、证据）→ 释放锁
```

每一步的进入与退出条件、证据、已知异常与处置在 workflow.json 中，看板上点击站点即可查看。

## 6. “不需要人工审查和合并”的授权链

一个版本自动落地，必须同时满足：
1. 用户事先批准了白名单与门禁（相当于 pstack 的全自主授权），且批准对应的内容没有被改动；
2. 评审通过：命令全在白名单内，没有触及红线，版本号连续，版本包新增内容没有命中停止规则，没有改动白名单与目标；
3. 可选的独立审查没有阻止；
4. 落地后门禁没有出现回归；出现回归就自动回退，不需要人；
5. 每一步都有证据与决策记录，事后可审计、可一条命令回退（wf undo）。

不可逆的事（资金、密钥、合规、实盘）不在这条链里，始终需要用户。

## 7. 档位与多模型

roles.json 定义角色到档位：设计与升级用深度档位（由预算决定，默认 max），常规实现与第一次修复用 high，节点与例行回报用 medium，续接沿用上一轮，探测用 low。Claude 的建议高于角色默认时采用较高者；例行情况下可以采用 Claude 建议的较低档位；5 小时窗口用量超过 85% 时，非失败情况封顶 high。每轮的角色、档位与理由写入轮次记录和决策日志，`wf effort` 按档位与角色给出轮次、通过率、平均消耗与耗时。数据积累后再据此调整 roles.json，而不是凭感觉。

“多模型”在我们这里只有两个可用的方向：同一模型的不同档位，以及执行端可以接入的另一个模型（独立审查适配器）。后者的价值来自模型系列不同，所以它只能增加阻力，不能代替门禁与判据。

## 8. 上下文

完整设计与给用户的说明见 CONTEXT.md（1.5.5）。

- 日常：PROJECT.md 是唯一真相源；每份回报自动附仓库指纹；指纹不一致时由 Claude 点名，执行端用 wf snapshot 发送有界的文件包。
- 对话体量：每轮累计字符与轮次；达到 policy 中的上限时驱动器停下，并自动生成恢复包（说明消息 + 仓库 zip）。用户开新对话后先 `wf conv new`，再上传 zip、发送说明消息，然后 `wf approve`。1.6.4 起，policy 的 auto_new_conversation 为 true 时由驱动器自己开新对话（适配器 conv_new），不再停下。
- 回复中断：驱动器自动发出“从断点继续”，不整条重发。

## 9. 低消耗

只在有事时发消息（计划节点、回报、续接）；全部通过时由【驱动指令】直接进入等待，不发确认消息；回报只嵌入输出末尾；档位按角色而不是一律最高；用量高时封顶；全局限速；轮询有间隔；同一问题连续失败就熔断，不空转；每日轮次上限。

## 10. 可观测

看板的“七类进度”对应：任务进度（项目视图的下一步与目标卡片）、流程进度（运行图与当前步骤）、交流内容（项目视图的对话记录）、互动进度（轮次时间线与轮次明细）、项目进度（项目视图、目标）、Agent 进度（Agent 卡片）、工具调用进度（对话记录中的工具标签与 Claude 卡片中的计数）。管理、跟踪、问题处理与交付分别在失败台账、需要注意、决策日志、版本记录与文档列表中。

## 11. 剩余风险

- 自动执行回复中的命令：能控制通道的人理论上可以借此执行命令。防线是白名单、红线、护栏、拼接拦截、版本包检查、熔断。白名单越宽，防线越弱。
- 批准无法在技术上区分用户本人与同一台电脑上的其他程序。
- 驱动器相信适配器的报告；适配器误报会导致错误推进。
- 门禁的强度取决于门禁本身：项目没有测试时，门禁只能查到导入错误与语法错误这一级。
- 对话体量只是上下文的近似指标，Claude 无法直接测量自己的上下文占用。

## 12. 后续可做
