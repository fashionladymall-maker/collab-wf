# 隔离开发、交接与验收规范

2026-10-15。本文记录已确定的开发方式和批次边界；历史产品目标仍以原项目的 VISION、PROJECT、BASELINE、LIVE、ISOLATION 和获批 goals 为准。接口机读表见 BATCH2_CONTRACT.json。本文不批准生产安装、权限扩大或恢复第149轮。

## 开发目标

让研发流程可连续推进、可核验、可恢复：每个任务能追溯来源、代次、负责人和证据；临时等待有检查点和有界恢复；结果不明的发送只核对和轮询；包、审查、安装使用同一份材料；机械自检、真实运行和用户验收分别记账。

问题闭环至少记录触发条件、可复现反例、原因、修复版本、回归测试和适用边界。只有实际复现关闭且回归通过才标为解决。新反例会重新阻断相关卡；不能以旧测试全绿代替新反例验证，也不承诺未知问题都能自动解决。

## 所有权与并行

Claude 主导架构和实现。A 负责任务代次、发送与仲裁、恢复、CLI 和执行消费；B 负责初始化、策略、包交接、审查与发布；C 负责目标分层、证据绑定、只读指标和总测试聚合。精确文件所有权以机读表为准。总架构可以承担已登记的 C 测试兼容任务，但不能与 C 同时写同一文件。

GPT 承担独立测试、反例、并发与可信边界审查、集成和证据核验。三个实现上下文独立生成；只有明确的 API 或共享文件依赖才串行。共享集成目录由协调端唯一写入。

每批使用独立开发根与集成分支，每张卡建立独立分支，并固定基线 commit/tree、文件白名单和验收项。共享目录中存在未提交改动时先核对作者、文件和字节，保留候选证据；不能用 hard reset 清掉未交接的工作。新卡从已确认基线启动，不能以分支同名代替字节相同。

## 小卡交付流程

1. 根据现有目标登记任务卡，冻结 owner、前置、允许文件、接口及回滚方法。
2. 给模型精确仓库、commit/tree 和必要上下文。输入气泡出现仅证明页面落地；必须核对最新请求标记、非发送失败、对应 DONE 和 streaming=false 后才消费结果。
3. 核补丁 SHA、逐文件前后 SHA、路径和权限；在隔离环境检查并应用，核多端字节一致。
4. 跑相关模块与实际正负例。状态身份、并发、发送和安装边界另做独立对抗审查；失败退回最小返工，原报告保留。
5. 检查公开内容后提交同仓库开发分支和 PR。PR 创建即登记到执行线程。集成必须绑定已审查的 head，合入后核实际 commit/tree。
6. 原实现会破坏既有测试时，由测试 owner 适配调用，保留断言意图；产品与必要测试兼容补丁一同合入和回滚。
7. 全批完成后跑组合自检、正规临时 MANIFEST/probes、真实默认门禁正反例、候选源码停用回退与恢复，并复核原现场边界。

Git 传输故障时可以用 GitHub Git 数据库接口交接，但必须核对 blob、tree 和 commit 与本地完全一致。不能覆盖不符的远端分支，不能把文件相似当成版本相同。

## 测试和结果标准

测试使用临时项目与 LOCAL，不调用真实生产发送或修改原安装。覆盖正常路径、缺失与坏数据、过期代次、并发交错、来源与内容漂移。并发关键性质用真实进程/文件锁或受控事件交错证明，不能靠 sleep 猜测。新回归能在旧实现上检出原缺陷；正常兼容路径也要继续通过。

Python 3.9 兼容性必须在真实解释器验证；最终组合还需核实目标 Mac 环境。测试记录绑定实际源码摘要、命令、环境、退出码、计数、时长和日志摘要。模块通过、整套通过和生产通过是不同结论。

C1 provider 格式为 c1-provider/1。每个必需类别要实际运行至少一个成功的正例和一个成功的负例，且无 provider 错误；缺项不能计为通过。聚合器由 C 唯一维护。嵌套探针最多一层，嵌套层排除门禁基线，更深层退出3。默认门禁正例必须在正规临时副本中重建 MANIFEST、init 项目并执行两条真实门禁，不能匹配固定文本冒充成功。

## 关键不变量

- 任务 generation、发送 lease 与轮次各有用途，不可互换。新任务写入核对项目根和代次；旧调用不能关闭重建任务。进度不冒充完成，中断任务需真实恢复。
- 外发前标记必须先在锁内持久化成功；持久化失败不能发送。已有标记、旧协议、未知或 WAIT_REPLY 不得当成未发送重试。新旧执行体混跑没有自动安全保证。
- 恢复期首次 since/deadline 不因进度、换规则或重启重置；额度等待仍保留发送身份并只轮询。同名不同规范根的项目不能互相重入、释放或回收有效租约。
- 策略批准不会豁免凭据、权限扩大、破坏或跨项目、错误项目和未核验安装等强门禁。正常已授权的项目内操作仍按精确范围处理。
- 安装使用统一宿主审查验证器，绑定冻结包、完整安装语义、目标实际基线、配置、规则及独立审查身份。模型自报或本地 HMAC 不是平台模型背书。缺可信来源返回 unknown 并拒绝；synthetic fixture 不能算真实平台验收。
- 目标至少有一个 exec 才可能 reached；空 all_exec 不能虚空 ready。批准且机械检查成功的默认骨架仍可人工验收。mechanical_pass、verified、NA 和人工确认不混用；严格实景失败不得靠窄映射遮盖。
- 依赖与 window_inputs 应绑定判定真正读取的数据和范围；坏行不静默跳过，未知影响保守失效。依赖验证器实现之前，不把设计声明当成已有能力。
- 指标必须有可证分母和来源。缺 ready/picked 协议时队列占比为 unknown；模型、额度、仲裁和网络等待分别记录，不冒充执行端排队。

## 模型调用

架构、可信边界、复杂恢复和依赖绑定采用 Claude Opus 5.5 最高努力；范围明确的普通卡采用高档。GPT 以 6.1 系列适当档位做独立审查与集成，高风险边界增加 Astra 反证。实际模型与努力档记录应如实区分当前运行配置、UI 选择和后端可信背书；不能把 UI 选择当成平台 attestation，也不能声称未实际切换的档位。
