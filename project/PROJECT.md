## 已确认结论
1. 交付方式：通道只能下载、不能上传，Claude 拿不到完整工具树。采用“补丁构建器”：单个 .py 文件，在已安装工具的 git 克隆上逐处应用锚点改动（每处必须恰好出现一次，否则整体中止），写入新文件，编译，跑完整自检，全部通过才打包，再由执行端 wf self-update。
2. 锚点可靠性：Claude 按已读原文重建文件，用 sha256 或 git blob 哈希核对逐字节一致，锚点才能一次命中。本对话已核对：core.py、projectmd.py、docs/WORKFLOW.md、项目的 4 个文件。
3. 读取工具文件：用 sed -n 起,止p 分片；1.5.0 起回报按约 32000 字符预算完整嵌入原文，超出部分自动续传。说明消息与回报嵌入都是逐字节无损的（第 1–2 轮实测，含反斜杠）。
4. 通道报“忙”时，最可能的情况是自己的上一条消息正在生成。带工具调用的长回复可达 20 分钟以上（第 40 轮实测 23 分钟），期间会话里看不到任何变化；updated_at、is_pending、消息数都不能证明“没有在生成”。第 1、9 轮补充：长生成期间流里只有心跳，适配器 300 秒的读取窗口先到期；会话的消息列表与 current_leaf 要到生成结束后才出现新消息，updated_at 在落地时就更新。原则：“已送达”的正面信号可以宽松采用（认错只是多等），“没送达”的结论必须严格（认错就会重复发送）。第 12 轮实测：发送后 3 秒 updated_at 即推进，与约 14 分钟后才出现的那条消息的 created_at 逐字相同，可作为落地的正面信号。
5. 发送结果不明时绝不自动重发。手动清除发送意图后重发，会造成重复消息（第 40 轮）。确认没有送达才用 wf resend（决定码加用户原话）。第 1 轮实测：驱动器的 NET 重试只排进队列，随后走 SEND_UNKNOWN_WAIT，全程只有一次发送。
6. 适配器的 ref 对 wf 是不透明字符串；需要适配器内部信息时，由 wf 原样交回（--prev-ref），由适配器解释。
7. 1.5.0 起事件先写状态再追加，只防中断造成的跳号；并发写入造成的重号由 1.5.2 的状态锁解决（W18）。历史记录里的重号与倒序不改。
8. 仓库指纹规则（ops.py:551–557）：git ls-files 排除 FP_EXCLUDE（含 workflow/wf.json）后，按“sha256 两个空格 路径”逐行拼接再取 sha256 前 16 位。第 4 轮由 Claude 独立重算一致。
9. 白名单（workflow/policy.json，决定码 8JJ，用户原话已记录）：工具文件用绝对路径 /Users/admin/.workbuddy-ai/tools/collab-wf/…，不用 ~；相对路径不能以点开头；grep 只能一个模式、一个文件，不带 -r 或 -e；git ls-files 不在名单内；; && || > < 一律需要批准，管道只能接 head、tail、grep、wc、sort、uniq、cut。

## 协作约定
通用流程与能力边界见 collab-wf 的 docs/（WORKFLOW.md、DRIVER.md、TRANSPORT.md、CAPABILITIES.md）。本项目特有约定：
- 工具版本只经构建器交付：锚点改动必须恰好命中一次；新文件整文件写入；构建器跑完整自检，全部通过才打包；1.5.9 起由驱动器 wf self-update --auto 安装，改动 wflib/floor.py 的版本停下等用户确认后手动安装
