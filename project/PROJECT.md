## 已确认结论
1. 交付方式：通道只能下载、不能上传，Claude 拿不到完整工具树。采用“补丁构建器”：单个 .py 文件，在已安装工具的 git 克隆上逐处应用锚点改动（每处必须恰好出现一次，否则整体中止），写入新文件，编译，跑完整自检，全部通过才打包，再由执行端 wf self-update。
2. 锚点可靠性：Claude 按已读原文重建文件，用 sha256 或 git blob 哈希核对逐字节一致，锚点才能一次命中。本对话已核对：core.py、projectmd.py、docs/WORKFLOW.md、项目的 4 个文件。
3. 读取工具文件：用 sed -n 起,止p 分片；1.5.0 起回报按约 32000 字符预算完整嵌入原文，超出部分自动续传。说明消息与回报嵌入都是逐字节无损的（第 1–2 轮实测，含反斜杠）。
4. 通道报“忙”时，最可能的情况是自己的上一条消息正在生成。带工具调用的长回复可达 20 分钟以上（第 40 轮实测 23 分钟），期间会话里看不到任何变化；updated_at、is_pending、消息数都不能证明“没有在生成”。第 1、9 轮补充：长生成期间流里只有心跳，适配器 300 秒的读取窗口先到期；会话的消息列表与 current_leaf 要到生成结束后才出现新消息，updated_at 在落地时就更新。原则：“已送达”的正面信号可以宽松采用（认错只是多等），“没送达”的结论必须严格（认错就会重复发送）。第 12 轮实测：发送后 3 秒 updated_at 即推进，与约 14 分钟后才出现的那条消息的 created_at 逐字相同，可作为落地的正面信号。
5. 发送结果不明时绝不自动重发。手动清除发送意图后重发，会造成重复消息（第 40 轮）。确认没有送达才用 wf resend（决定码加用户原话）。第 1 轮实测：驱动器的 NET 重试只排进队列，随后走 SEND_UNKNOWN_WAIT，全程只有一次发送。
6. 适配器的 ref 对 wf 是不透明字符串；需要适配器内部信息时，由 wf 原样交回（--prev-ref），由适配器解释。
7. 1.5.0 起事件先写状态再追加，只防中断造成的跳号；并发写入造成的重号由 1.5.2 的状态锁解决（W18）。历史记录里的重号与倒序不改。
8. 仓库指纹规则（ops.py:551–557）：git ls-files 排除 FP_EXCLUDE（含 workflow/wf.json）后，按“sha256 两个空格 路径”逐行拼接再取 sha256 前 16 位。第 4 轮由 Claude 独立重算一致。
9. 白名单（workflow/policy.json，决定码 8JJ，用户原话已记录）：工具文件用绝对路径 /Users/admin/.workbuddy-ai/tools/collab-wf/…，不用 ~；相对路径不能以点开头；grep 只能一个模式、一个文件，不带 -r 或 -e；git ls-files 不在名单内；; && || > < 一律需要批准，管道只能接 head、tail、grep、wc、sort、uniq、cut。

## 已排除方案及原因
- 迁移到官方 API：用户决定继续使用现有网页通道（第 34 轮）。
- 把工具仓库公开到 GitHub 以便 Claude 克隆：本机未登录，且与“不引入远程仓库”的约定冲突（第 39 轮）。第 25 轮用户改变决定，交接包改经公开 GitHub 仓库交付（已确认结论 19）。
- 让驱动器自动执行 approve、force、unpause 来实现“护栏全自动”：底线命中后停下等的正是 approve，自动批准等于底线形同虚设（第 22 轮）。改为已确认结论 17 的不变量。
- 用 macOS 通知提醒用户：用户第 21 轮否定，接收者应是执行端；而执行端看不到屏幕通知（已确认结论 18）。
- 用“三个探针同时静止”判定孤儿锁并调用“停止生成”：第 40 轮证明这三个探针在真实生成期间同样静止，会误杀进行中的回复（F22 继续有效）。
- 把 workflow/ 放进工具仓库：会让 MANIFEST、self-check 与升级前的工作区检查都要开例外，破坏“装上的就是版本包”的核验。
- wf resume 直接放行待批准的命令：会绕过“决定码加用户原话”的批准门。
- 只在 event() 里重读 seq：能治重号，治不了驱动器用过期的整份状态覆盖 wf pause（第 5 轮，W18）。
- 在命令后加 || true 避免 grep 无匹配算失败：会掩盖真失败，白名单也拦截 ||（第 6 轮）；改为判据写 exit=1（W21）。
- 适配器按内容比对没找到消息就返回“没送达”、驱动器直接阻塞（执行端第 10 轮提出后自行撤回）：生成结束前会话的消息列表本来就不含新消息，这正是假阴性，会导致重复发送。

## 协作约定
通用流程与能力边界见 collab-wf 的 docs/（WORKFLOW.md、DRIVER.md、TRANSPORT.md、CAPABILITIES.md）。本项目特有约定：
- 工具版本只经构建器交付：锚点改动必须恰好命中一次；新文件整文件写入；构建器跑完整自检，全部通过才打包；1.5.9 起由驱动器 wf self-update --auto 安装，改动 wflib/floor.py 的版本停下等用户确认后手动安装
- 改动某个行为之前，先在 wflib/selftest*.py 中检索相关子命令与提示文字，把会被影响的旧断言一并列入改动并在摘要中写明；原有检查不删除、不跳过
- 锚点只用读到的原文；能重建的文件先用 blob 哈希核对逐字节一致
- 回报清单第 N 项对应【本机执行】第 N 条命令；驱动指令的“验收 N”与之一一对应；命令按白名单写（已确认结论 9），可能无匹配的检索把判据写成 exit=1，或改用 sed、cat
- 阻塞本轮的用户决定只用“（前置）”标记
- 执行端转述用户的原话时，用 wf said 逐字记下（看板“对话记录”的“用户”）；Claude 不替用户写原话
- 回复尽量短：长生成会让发送超时、触发“结果不明”
- Claude 不审读通道适配器的站点接口代码，只约定接口；适配器的实现由执行端负责
- 发送结果不明时不重发、不做探测发送；需要重发只用 wf resend
- 开新对话：先 wf conv new，再发送说明消息；等说明消息的回复落地后再 wf approve（W39）
- 计划节点只等外部条件；需要执行端手动操作时写“之后：空闲”，执行端做完用 wf kick --kind report 回报（W23）
- Claude 每次交付前先确认文件在交付目录里，再交付（W24）
- 已交付的版本号不再复用：内容变了就用下一个版本号（W29）
- 驱动器执行的命令里，Python 一律写 3.13.12 的绝对路径；工作目录是项目根
- 交接仓库是公开的：只放已提交的项目文件、工具版本包与说明消息；不放 local/（transport.json、会话凭据、快照）、workflow/evidence/ 与任何密钥
- 工具版本：Claude 先在公开仓库的最新工具包上跑构建器与完整自检，通过后再交付（已确认结论 25）
- 方案以用户真实环境与当前计划为前提：扩展只做“加”，不删、不抽象掉正在用的东西；不拿 Claude 容器里的环境当作对用户现状的判断（W36）
- 查事件与人工动作一律用 wf audit（白名单内）（W40）
- 回报、PROJECT.md 与交付物不写本机凭据机制与内部接口的细节（W41）
- 写给执行端的事一律写成【驱动指令】里的“执行端 N：<事项>”（1.6.6 起），正文只作说明（W44）
- Claude 看不到本机发送日志：PROJECT.md 写发送层面的细节（时刻、事件流内容、是否接受）只用回报原文或独立审查核对过的日志，不凭“需要注意”的摘要推断（第 63–65 轮连续三次审查意见）
- 回报“需要注意”里的自动处置可能属于上一条发送：引用时按发送时刻核对是哪一条，不按回报的轮次号归属（v2.4 独立审查意见）
- 轮次口径：PROJECT.md 记安装与实测的轮次，按带回原文的那份回报计（turns/turn-NNN.md）；证据轮次按实际的证据目录或绑定记录写，不假定固定偏移（执行端待办的结果可能在当轮、迟到或跨轮）；需要时两者都写（第 61、63 轮独立审查意见）
- Claude 在自己容器里运行的读取与解包命令一律加超时；新对话首轮只做必要的核对（W45）
- 执行端代用户决定时如实写明是执行端的决定，不借用用户别的话当 --said；1.6.5 之前在 wf note 里注明“执行端代决”（W43）
- 执行端的备份与临时产物放在被忽略的目录（local/、workflow/evidence/）或项目树之外，不放在已跟踪的文件旁边；否则落地前会被自动存进版本库并同步到公开仓库（W52）
- 目标达成后交回结果用 wf kick --kind report（1.7.1 起，由证据生成）；说明先用 wf note --kind info 写。不手写“终端原文”：需要原文的内容用 wf exec 跑，或明确标成转述（W53）
