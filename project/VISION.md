## 一、定位

collab-wf 是一个**让大模型做设计与编码、让本机按可审计的规则执行与验收**的工作流引擎。公开的是引擎与它的规则，不是我们这一套具体的工具组合。

对外的三个角色：

| 角色 | 是谁 | 做什么 |
|---|---|---|
| 设计端（Planner） | 一个大模型，经“通道”接入 | 方案、全部代码、结果解读；每轮按固定六块回复 |
| 驱动器（Runner） | 本机上的 collab-wf | 发送、等待、评审、落地、执行、取证、验收、回报；按白名单与停止底线决定能不能自动做 |
| 负责人（Owner） | 用户本人 | 资金、密钥、合规、平台、通道的决定；批准白名单与目标；最终验收 |

我们现在的“执行端”（一个本机 AI 代理）在公开版里是**可选的协助者**：驱动器处理不了的异常经 inbox 交给它。没有它，异常就交给负责人。“执行端”“WorkBuddy”这些词不进入公开版的核心概念。

## 二、关键决定（对应执行端提出的 7 个问题）

1. **定位**：见第一节。公开引擎与规则；角色用设计端、驱动器、负责人表述。
2. **大脑**：选 (c)，但内置的只做**官方 API 适配器**（先 Anthropic Messages API；之后视需要加 OpenAI 兼容端点），同时保留并文档化外部适配器接口（adapters/base.py）。**公开版不内置、不文档化任何驱动网页聊天界面的适配器**：那不是这些服务支持的用法，界面随时会变，也不能要求陌生人承担这个风险。我们自用的通道是用户的决定，继续放在工具目录之外。
   API 通道还顺带解决两个老问题：对话由本机保存和裁剪，开新对话不再需要人（W34 的根源）；附件不再是问题（交付物以回复中的文件块落地，见 1.8.0）。
3. **跨平台**：抽象成调度后端。所有平台都能用 `wf run --loop`（前台常驻）；另外生成 launchd（macOS）、systemd 用户单元与 cron（Linux）的配置。Windows 排在最后，先保证 `wf run --loop` 在 Windows 上可用。系统通知保持可选，inbox 文件是跨平台的通用信号。
4. **去个人化**：WorkBuddy、aimonkey、c.aimonkey.plus 不出现在公开版的代码、文档和看板里；文档里需要举例时说“本机 AI 代理”“对话通道”。我们自己的这些适配器继续放在工具目录之外，由 local/transport.json 指向。
5. **发布形态**：
   - 产品源码用一个干净的公开仓库，只放工具本身；现在的 `collab-wf` 公开仓库是 collab-wf-dev 的上下文镜像，建议改名为 `collab-wf-dev`（或新建产品仓库），两者分开。
   - 工具只用 Python 标准库（3.9+），依赖声明就是一个 pyproject.toml，没有第三方依赖；`pip install` 后得到 `wf` 命令。上 PyPI 排在 2.0.0。
   - License 由用户决定（见第四节）。
6. **路线图**：见第三节。
7. **与 M1 的关系**：M1“自用跑顺”保持不变、先达成；公开化作为 **M2**，按版本列出可执行判据，M1 达成（进入“目标达成”）后由负责人批准 M2 的 goals.json 接上。两者的开发可以并行：M1 只是计数，不阻塞写代码。

## 三、路线图（每版的验收判据在看到结果之前写死）

| 版本 | 主题 | 内容 | 验收判据 |
|---|---|---|---|
| 1.7.0 | 能装上、能看到一轮跑通 | pyproject.toml（零第三方依赖，入口 wf）；面向陌生人的 README（是什么、为什么、5 分钟上手）；`wf demo`：用内置的模拟通道在临时目录里完整跑一轮（发送、回复、评审、落地、执行、验收、回报），不需要任何大模型与密钥 | 在干净的 Linux 与 macOS 环境中：`pip install` 仓库地址 → `wf demo` 退出码 0 并打印“演示轮次完成”；完整自检全部通过 |
| 1.8.0 | 官方大脑 | adapters/anthropic_api.py（内置）：发送、等待、额度三个动作映射到 Messages API；对话历史本机保存、按体量自动裁剪与续接（开新对话不再需要人）；回复中的文件块（带路径的代码块）落地为交付文件；密钥只从环境变量读取 | 自检用模拟的 HTTP 服务全部通过；负责人提供密钥后，真实跑通一轮（回复解析出六块、交付文件落地）；全程没有密钥进入任何消息、日志或同步内容 |
| 1.9.0 | 跨平台调度 | `wf run --loop`；`wf schedule plist / systemd / cron`；inbox 作为默认通知；文档按平台分节 | Linux（systemd 用户单元或 cron）与 macOS（launchd）上定时推进各自连续 3 轮；Windows 上 `wf run --loop` 跑通 `wf demo` |
| 1.10.0 | 去个人化与文档 | 去掉 WorkBuddy、aimonkey 等词；英文 README 与上手文档（中文文档保留）；CONTRIBUTING、问题模板；GitHub Actions 在 Linux 与 macOS 上跑完整自检 | 全仓库检索不到这些私有名词；CI 在两个平台上全绿；一位没有参与过的人只读 README 完成 `wf demo` |
| 2.0.0 | 公开发布 | 产品仓库正式发布、打标签；PyPI 发布；版本兼容承诺（项目数据格式） | 从 PyPI 安装的 `wf demo` 跑通；发布说明列出已知限制 |

M2 的 goals.json 会把上表的判据逐版写成 exec 目标（例如“在临时虚拟环境里 pip install 后 wf demo 退出码 0”），M1 达成后交负责人批准。

## 四、需要负责人决定的事

1. **License**：MIT（最简单、最宽松）或 Apache-2.0（宽松，另含专利授权条款，企业用户更常要求）。两者都允许任何人使用、修改、商用。这是法律与平台层面的决定，由负责人定；2.0.0 公开发布之前要定，不阻塞 1.7.0 的开发。
2. **1.8.0 的真实验证需要一个 Anthropic API 密钥**，按用量计费（一轮的消耗与现在一条长回复相当）。密钥只放本机环境变量，不经任何聊天通道。是否提供、额度上限多少，由负责人定；不阻塞 1.7.0。
3. **仓库安排**：现在的公开仓库 `collab-wf` 是上下文镜像；产品源码是另建仓库，还是把镜像改名后让产品使用 `collab-wf` 这个名字。2.0.0 之前定。
