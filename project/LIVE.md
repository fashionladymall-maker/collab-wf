# LIVE.md —— 实景验收：怎样才算“真的跑起来了”（设计 v1，第 119 轮）

用户第 118 轮：“又不了了之了，漏洞太大 bug 太多，根本没跑起来。”此前的“通过”大多是隔离环境里的自检与探针（mechanical_pass）。本文件定义实景验收（verified）：在用户真实的 macOS、真实通道、真实执行端上，连续几个正式轮次的全链路，按日志与证据逐条机检。自检与探针仍然要跑，但不再拿来宣称完成。

## 1. 一轮的闭环（逐段都要有证据）

| 段 | 判据 | 证据从哪里来 |
|---|---|---|
| 1 只发一次 | 本轮在适配器日志里只有一次 send，没有 wf resend；防重发守卫没有拦截记录，或拦截了且只发出一次 | 适配器动作日志、send_dedup 账本、turns.jsonl |
| 2 回复归属 | 回复写回的回执码与本轮发出的逐字一致；reply_parent 与 send_ref 一致 | intake.json、reply_meta.json、事件 |
| 3 交付一致 | 声明的交付文件都送达、sha256 一致；没有 RELEASE_MISSING、FP_MISMATCH | intake 的交付核对、落地事件 |
| 4 审查在先 | 本轮安装的工具版本在安装前已有审查结论（pass 或 concerns）；没有安装时写 not_applicable 与理由 | 审查记录；没有 unreviewed 留档 |
| 5 无人工改动 | 本轮没有执行端或用户的状态改动、手工执行、手工落地、手工发送（四道底线的批准除外） | wf audit 的 by 字段 |
| 6 计划未过时 | 没有 PLAN_STALE；命令按计划执行完或按判据停下 | 事件、证据目录 |
| 7 待办闭合 | 本轮登记的执行端待办都用 wf task done、cancel、supersede 关闭，在依赖它的回报之前关闭 | executor_tasks、事件顺序 |
| 8 回报自动 | 回报由工具从证据生成（驱动器自动或 wf kick --kind report），不是手写；没有重复送达 | 事件、turns.jsonl |
| 9 发现及时 | 回复结束到被接上不超过预算（建议 5 分钟） | 适配器日志与事件时刻 |
| 10 同步 | 本轮同步带提交号推送成功 | local/sync 记录 |

## 2. 怎样算通过

- 连续 3 个正式轮次，每一轮第 1–10 段全部达标，中间没有任何一轮失败；任何一段不达标，计数从零重来。
- 其中至少 1 轮包含一次工具版本的“构建—审查—安装”，至少 1 轮包含一次项目版本落地。
- 期间执行端可以在场，但不做第 5 段列出的人工动作。

## 3. 测量

1.9.0 提供只读命令 wf live-check [--rounds 3]：读事件、轮次记录、证据目录、审查记录、同步记录与适配器动作日志（transport.json 的 log），逐段输出“达标 / 不达标（原因与证据位置）”，全部达标退出码为 0。它只读、不改任何状态；作为 M2 的实景目标 M2-R1 的检查命令，需要加进白名单（扩大权限，按决策顺位批准）。

## 4. 多项目实景（之后的阶段）

两个受控的测试项目（不用 Amy，不用模拟盘），共享发送槽开启（shared_max_inflight=1），同时推进至少 2 轮：两边都满足第 1 节，arbiter.jsonl 里有 wait、grant、release，两个项目的对话、待办、inbox、同步仓库互不串（ISOLATION.md 的 I1–I8）。

## 5. 不算实景的东西

自检数量、探针通过、离线回归、单次手工演示、执行端的口头确认、kick 排队成功、事后补审的 pass。
