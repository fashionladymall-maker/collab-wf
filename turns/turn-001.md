===== WORKFLOW.md =====
# WORKFLOW.md —— Claude（设计与编码）× 执行端（部署与验收）协作规则

本文件属于 collab-wf 工具，对所有项目通用。项目特有的约定只写在各项目 PROJECT.md 的"协作约定"里。
怎么安装、怎么调用见 USAGE.md；每一步的完整机器可读定义在工具根目录的 workflow.json（`wf step <状态>` 查看）。

## 1. 角色

Claude 负责方案设计、全部代码、结果解读、决策建议，并维护 PROJECT.md 与 CHANGELOG.md。
执行端负责落地版本、执行命令、收集证据、验收、回报，维护桥接工具；不写业务代码，可以提意见。
用户负责一切涉及资金、密钥、合规、平台、通道的决定，以及最终验收；批准白名单与目标定义；随时可以暂停、回退、接管。
驱动器（1.1.0 起）代替执行端完成例行步骤：由系统定时唤醒，按状态自动推进，遇到需要用户的事就停下。设计与边界见 DRIVER.md。

## 2. 唯一真相源

| 内容 | 位置 | 维护方式 |
|---|---|---|
| 工作流规则与定义 | collab-wf 工具目录（自己的 git，版本标签 wf-vX.Y.Z） | Claude 交付，执行端用 wf self-update 安装 |
| 项目代码 | 项目 git 仓库（每个版本一个提交与标签 vX.Y） | Claude 交付，执行端用 wf apply 落地 |
| 项目状态与决策依据 | 项目 PROJECT.md（固定九章，可校验） | Claude |
| 工作流运行状态 | 项目 workflow/state.json（当前位置）与 events.jsonl（全部事件，只追加） | wf 命令自动写入 |
| 对话、轮次、证据 | workflow/transcript.jsonl、turns.jsonl、evidence/ | wf 命令自动写入 |

Claude 的运行容器可能在轮次之间重置，权威副本永远在本机。

## 3. 工作流总览

一轮由八个步骤组成，首尾相接；另有五个等待或阻塞状态。

```
 ┌→ 组织消息 → 发送 → 等待 Claude → 接收与解析 ┐
 │                                              ↓
 └─ 验收 ← 执行与取证 ← 落地版本 ← 执行前评审 ←─┘
 等待区：空闲 / 等待计划节点 / 等待用户决定 / 等待额度重置 / 阻塞
```

| 步骤 | 负责 | 退出条件（摘要） | 失败上限 |
|---|---|---|---|
| COMPOSE 组织消息 | 执行端 | 草稿通过 check-outgoing | — |
| SEND 发送 | 执行端 | 通道已接受消息（不以“可见”为准） | 3 次 |
| WAIT_REPLY 等待 Claude | Claude | 回复结束 | 2 次 |
| INTAKE 接收与解析 | 执行端 | 五个固定块齐全，交付文件完整 | — |
| REVIEW 执行前评审 | 执行端 | 评审已接受（需用户批准的已获批准） | — |
| APPLY 落地版本 | 脚本 | 提交成功且 PROJECT.md 校验通过 | — |
| EXECUTE 执行与取证 | 执行端 | 命令全部执行或在失败处停止 | — |
| VERIFY 验收 | 执行端 | 回报清单每项都有结论 | — |

每进入一次 COMPOSE，轮次加一。失败次数达到上限自动进入 BLOCKED；需要用户批准的命令自动进入 AWAITING_USER。
不合法的转换会被拒绝，并提示允许的去向；确需更正时用 `wf force`，看板会把它标为人工更正。
每一步的做法、进入与退出条件、证据、已知异常的判定与处置，都在 workflow.json 中，`wf step <状态>` 或在看板上点击站点即可查看。

## 4. 一轮的标准做法

自动：系统定时器运行 `wf tick`，下面每一步都由驱动器完成（DRIVER.md）。手动（驱动器暂停或未启用时）：

```
wf report                                  # 由证据生成回报草稿（进入 COMPOSE）
wf check-outgoing <草稿> --kind report     # 密钥扫描、结构、版本与档位
（桥接工具发送）→ wf mark sent --message-file <草稿> --kind report --effort high --model <模型>
（桥接工具等待）→ wf mark replied --reply-file <回复全文>
wf intake <回复全文>                        # 解析五个固定块，齐全时进入 REVIEW
wf review → wf review --accept              # 命令风险分级
wf apply <zip>                              # 有交付版本时
wf exec -- '<命令>'                         # 每条命令一次，自动取证
wf verify set <序号> pass|fail|deviation|skip --evidence cNN
wf report                                   # 下一轮
```

计划节点：需要回报时，等 Claude 回复后在评审之后 `wf wait`；不需要回报时，验收后直接 `wf wait`。Claude 在指令中必须写明本轮是否需要回报，两者不能同时要求。

## 5. 消息规范

**"完整上下文"的含义**：同一个对话里 Claude 能看到全部历史，需要的是本轮全部新信息、终端原文、与预期的偏离、当前版本号，不需要重复历史。只有开新对话时才完整重建（第 10 节）。

**Claude 每轮固定输出六块**（wf intake 按这些标题解析）：【本轮结论】【本机执行】【本轮回报清单】【需要用户决定】【下一轮建议档位】【驱动指令】。【本机执行】中的命令放在代码块里，每条一行，不用 && ; > 等拼接（拼接会让驱动器停下等用户），也不写 wf intake / review / apply / wait 这类由驱动器负责的步骤；【本轮回报清单】与【需要用户决定】用编号列表，阻塞本轮的用户决定标注“（前置）”；没有内容时写"无"。【驱动指令】的格式见 DRIVER.md 第 5 节：每个清单项尽量给出机器判据，并写明本轮之后是回报、等待还是空闲。

**执行端回报**：wf report 生成三段式草稿：① 环境障碍与偏离 ② 关键数字与终端原文 ③ 需要决策的点。原文由证据自动嵌入；执行端的解读放在原文之后。

## 6. 档位策略

| 档位 | 用于 |
|---|---|
| low | 通道探测、确认收到 |
| medium | 例行回报：完全没有异常，且下一步已事先确定 |
| high（默认） | 写代码、改代码、解读结果、带任何异常的回报 |
| max | 方案设计；high 下一次没解决的疑难问题；不可逆决策（上实盘、动资金、换平台） |

"例行"指完全没有异常，不只是清单达标。wf report 在出现失败、偏离或未通过项时自动建议 high。
待验证假设：额度消耗主要取决于生成量，档位与任务大小都通过生成量起作用。看板的档位统计（平均消耗、平均耗时、每分钟消耗）攒够十几轮、覆盖多个档位后，再据此修订本节。

## 7. 发送、长等待与额度

一次只发一条，发送前确认上一条回复已结束。一轮可能持续半小时以上，超过 45 分钟没有新内容才算异常。
发送被拒、消息延迟出现、额度用尽、回复中断的判定与处置，见 workflow.json 中 SEND 与 WAIT_REPLY 的异常表。
额度用尽的标准动作是等待窗口重置（QUOTA_WAIT），不轮换账户。回复中断时发"从断点继续"，不整条重发。

## 8. 记录文件

全部由 wf 命令自动写入，执行端不再手工记账：发送与收到由 `wf mark` 记录（含实测耗时与发送前后的额度），执行由 `wf exec` 记录，状态转换写入 events.jsonl。usage.json 由桥接工具在查询额度后覆盖写入，wf 只采用 10 分钟内更新过的数据。

记录文件只写实测值；缺失比估算好，因为估算值一旦进入统计，就分不清哪些数字可信了。

## 9. 质量与可靠性

- 先校验后落地：wf apply 在复制任何文件之前校验 PROJECT.md，失败时仓库不被改动。
- 每个版本一个 git 提交与标签；项目与工具都可以回滚，回滚生成新提交，不改写历史。
- 证据自动采集：每条命令的输出、错误、退出码、耗时都保存在 evidence/，回报引用原文。
- 判定标准在看到结果前写死；验收逐项给出结论与证据编号。
- 执行前评审拦截资金、密钥、实盘类命令，必须由用户批准。
- 发送前密钥扫描：疑似密钥的消息不能被记为已发送。
- 工具升级前先运行新版本的端到端自检，不通过不安装。
- wf doctor 检查版本匹配、PROJECT.md、工作区、当前步骤是否超时、项目进程是否在运行。

## 10. 上下文保持与恢复

日常保持靠四样东西：PROJECT.md（结论与决策依据）、git 历史（代码）、events.jsonl 与 evidence/（发生过什么、原文是什么）、本文件（规则）。
需要开新对话时（对话太长、持续报错、回复明显对不上上下文）：

1. `wf bootstrap --reason "原因"`：生成说明消息（含本文件与 PROJECT.md 全文、工作流当前位置与下一个计划节点）、项目仓库 zip（只含已提交文件，不含数据与密钥）、collab-wf 工具本身的 zip。
2. 在新对话中上传两个 zip 并发送说明消息，档位用 max。执行端把桥接工具指向新对话，然后 `wf conv new --note …`。
3. Claude 第一轮只做三件事：复述版本、阶段与待用户决策；确认 zip 与 PROJECT.md 一致；给出下一轮指令。
4. PROJECT.md 与事实不符时，以 git 历史与 evidence/ 中的原文为准，由 Claude 修正后发布新版本。

同一对话中的同步检查：每份回报自动附带仓库指纹，Claude 与自己的副本比对；不一致时由 Claude 点名文件，执行端用 wf snapshot 发送有界的文件包（USAGE.md 第 10 节）。不引入远程仓库：私有仓库需要经聊天传递凭据，公开仓库会公开代码。

## 11. 版本与回滚

项目：`wf apply <zip>` 落地；`wf rollback --to vX.Y` 回滚。交付 zip 可带 RELEASE.json，其中 delete 列出要删除的文件，notes 写说明；wf apply 只按清单删除，不会删除清单外的文件。
工具：`wf self-update <zip>`（先自检后安装，打标签 wf-vX.Y.Z）；`wf self-rollback <版本>`。
项目在 workflow/wf.json 中固定工具的主次版本（如 1.0）。版本不一致时，看板与 wf doctor 会提示：次版本不同时阅读工具 CHANGELOG 后 `wf pin`；主版本不同时先回滚工具或等 Claude 给出迁移说明。

## 12. 决策原则

1. 只做可能改变决策的分析。
2. 判定标准在看到结果之前写死。
3. 回报给原文，不只给转述。
4. 资金、密钥、合规、平台、通道由用户本人决定；任何聊天通道都不传输密钥。

## 已确认结论
1. 交付方式：通道只能下载、不能上传，Claude 拿不到完整工具树。采用“补丁构建器”：单个 .py 文件，在已安装工具的 git 克隆上逐处应用锚点改动（每处必须恰好出现一次，否则整体中止），写入新文件，编译，跑完整自检，全部通过才打包，再由执行端 wf self-update。
2. 锚点可靠性：Claude 按已读原文重建文件，用 git hash-object 与 ls-tree 的 blob 哈希核对逐字节一致（core、machine、ops、admin、anomaly、bootstrap 模板均已核对），锚点才能一次命中。
3. 读取工具文件：用 sed -n 起,止p 分片；1.5.0 起回报按约 32000 字符预算完整嵌入原文，超出部分自动续传。
4. 通道报“忙”时，最可能的情况是自己的上一条消息正在生成。带工具调用的长回复可达 20 分钟以上（第 40 轮实测 23 分钟），期间会话里看不到任何变化；updated_at、is_pending、消息数都不能证明“没有在生成”。
5. 发送结果不明时绝不自动重发。手动清除发送意图后重发，会造成重复消息（第 40 轮）。确认没有送达才用 wf resend（决定码加用户原话）。
6. 适配器的 ref 对 wf 是不透明字符串；需要适配器内部信息时，由 wf 原样交回（--prev-ref），由适配器解释。
7. 1.5.0 起事件先写状态再追加；历史记录里的 6 处重号、2 处倒序是此前留下的，不改。

## 协作约定
通用流程与能力边界见 collab-wf 的 docs/（WORKFLOW.md、DRIVER.md、TRANSPORT.md、CAPABILITIES.md）。本项目特有约定：
- 工具版本只经构建器交付：锚点改动必须恰好命中一次；新文件整文件写入；构建器跑完整自检，全部通过才打包；安装由执行端手动 wf self-update（护栏命令）
- 改动某个行为之前，先在 wflib/selftest*.py 中检索相关子命令与提示文字，把会被影响的旧断言一并列入改动并在摘要中写明；原有检查不删除、不跳过
- 锚点只用读到的原文；能重建的文件先用 blob 哈希核对逐字节一致
- 回报清单第 N 项对应【本机执行】第 N 条命令；驱动指令的“验收 N”与之一一对应
- 阻塞本轮的用户决定只用“（前置）”标记；不阻塞的决定里不写“阻塞”二字（W15 修复前）
- 回复尽量短：长生成会让发送超时、触发“结果不明”
- Claude 不审读通道适配器的站点接口代码，只约定接口；适配器的实现由执行端负责
- 发送结果不明时不重发；需要重发只用 wf resend
