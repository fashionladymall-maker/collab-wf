## 用户新增的真实要求（必须落实）

用户原话：
“具体是要什么样的图呢？我希望你自己能够去推理。我是小白，能够让我看得懂又专业。软件开发中所用的所有图，工业流程中所用的所有的图，你都应该知道是什么样的图。所以你都推理出我的需求，再完整的交付给 Cloud。”

含义不是机械增加几个图名，而是：
1. 先由你主动判断这个工具对初学者真正需要的图谱；
2. 用专业图种表达软件开发、自动化驱动、消息交互、证据/质量、异常恢复、工业流程的关键关系；
3. 每个图必须有明确教学问题、读图顺序、图例和“何时不适用”；
4. 不为了“所有图”而堆砌，选择一套覆盖全面但能讲清楚的最小完备图谱；
5. 让小白先看全景，再逐层理解局部、角色、时序、状态、数据/证据、异常、闭环效果。

## 请主动推理并补齐的图谱体系

请在 HTML 中增加“为什么需要这些图 / 阅读路线 / 图谱地图”一章或一组前置导航，并至少整合以下专业图种。名称可以用更准确的中文，但不能省略教学目的：

A. 全景架构图（System / Context Architecture）
- 讲清用户、WorkBuddy 执行端、collab-wf 驱动器、Claude、适配器/通道、项目仓库、看板、inbox、看门狗和本机调度的边界。
- 标清谁是大脑、谁是手脚、谁是独立观察者；哪些是教学模拟，哪些是本机真实事实。
- 初学者要能回答“到底有哪些角色、谁给谁发什么”。

B. 端到端业务/工业流程图（BPMN/泳道式）
- 用用户需求进入、拆解、发送、回复、审查、落地、执行、取证、验收、回报、下一轮的完整主路径。
- 用泳道区分用户、驱动器、Claude、执行端、系统调度/看门狗。
- 说明异常分支和四道底线，不要将普通 AWAITING_USER 误解为所有事情都退给用户。

C. 状态机图（State Machine）
- 保留八主状态 COMPOSE→SEND→WAIT_REPLY→INTAKE→REVIEW→APPLY→EXECUTE→VERIFY，以及六个停留状态 IDLE、WAIT_SCHEDULE、AWAITING_USER、QUOTA_WAIT、BLOCKED、DONE；说明 pause 是独立标志。
- 用可点击场景解释合法转移、停留、恢复、正常 DONE 与故障 BLOCKED 的区别。

D. 时序/交互图（Sequence / Interaction）
- 展示消息、父消息归属、回复落地、迟到回复、SEND_UNKNOWN_WAIT、SEND_NOT_LANDED、事件唤醒、tick、看门狗和自动回报。
- 说明“未确认落地”不是确定没送达，不能仅凭不可见自动重发；第 72 轮 08:02→08:19作为真实案例但不暴露凭据。

E. 数据流/证据链图（DFD / Evidence Lineage）
- 把任务文件、outbox、桥接日志、消息 UUID/父 UUID、reply、evidence/c01/c02、review_adapter、verify、inbox、看板状态串起来。
- 让初学者理解“不是说完成了，而是每一步留下可核对的证据”；区分源数据、派生状态、教学模拟数据。

F. 质量门禁与独立审查图（Quality Gates / Review Pipeline）
- 清楚画出白名单/底线/包检查→独立模型审查→门禁基线→落地→门禁复查→执行→验收。
- 明确 pass/concerns/block/timeout/unreviewed 的语义；当前项目 gates=[]，门禁空过，门禁回退仅已实现未实景，不能画成每轮都已实景运行。
- 标明另一模型系列审查与 Claude 的职责边界。

G. 异常/恢复决策树（Fault Tree / Recovery Decision Tree）
- 覆盖网络暂态、结果不明、迟到回复、未确认落地、项目锁、配额等待、每日 24 轮 QUOTA_WAIT、看门狗发现、审查 block/timeout、四道底线。
- 给出“执行端先查什么、何时可自行代决、何时只能升级用户”的顺序；不把用户授权扩展到资金/密钥/合规/实盘。

H. 事件驱动与看门狗图（Event / Control Loop）
- 区分本机 launchd tick 每 60 秒、执行端事件唤醒及 5 分钟兜底、独立 watchdog 每 300 秒、WorkBuddy 每小时兜底；不要写成同一个定时器。
- 解释“被观察者卡死时为什么需要独立观察者”，以及投递成功和记已报必须分开。

I. 证据时间轴/甘特式图（Timeline）
- 以第 72 轮迟到回复和第 73 轮修订为例，展示发送尝试、回复落地、验收、修订的相对顺序；避免把容器自测写成本机实测。
- 用“已实景验证/仅 Claude 自测/待本机验证/待开发”图例。

J. 多项目/部署拓扑图（Deployment / Multi-project Topology）
- 解释一个驱动器如何服务多个项目、项目锁如何避免并发、仓库同步与本机事实如何核对；不把公开仓库滞后一律解释成缓存。
- 说明本教程是离线教学模拟，不会连接真实项目。

K. 飞轮/闭环效果图（Feedback Loop / KPI Dashboard）
- 保留现有飞轮和效果图，但补足“输入→执行→证据→反馈→更稳的下一轮”；数值是教学模拟，不能冒充生产 KPI。

## 图谱设计要求

1. 必须有一张“图谱地图/阅读路线”：
   - 先看 A 全景架构；
   - 再看 B 端到端泳道；
   - 再看 C 状态机；
   - 再看 D 时序；
   - 再看 E 证据链与 F 质量门禁；
   - 最后看 G 异常恢复、H 事件看门狗、I 时间轴、J 多项目、K 飞轮效果。
   - 每张图写“它回答什么问题”和“不要用它回答什么问题”。
2. 对小白：图中术语旁边给一句白话；同一角色/颜色/形状在各图保持一致；提供图例；可点击节点显示释义。
3. 对专业性：使用合理的 UML/BPMN/DFD/时序/状态机/决策树/拓扑/时间轴语义，但不要为了格式而牺牲可读性。
4. 交互能力保持：播放、暂停、上一/下一步、复位、调速、场景切换、节点释义、图 A/C 完整高对比视图；新增图如使用动画，也必须有逐步控制和无障碍文字说明。
5. 浅色背景深色文字、响应式；桌面和 390px 手机不产生全页横溢出；图内横向大图可以局部滚动但须提示。
6. 完全离线自包含，无 CDN、无外部脚本、无真实系统操作、无凭据、无远程输入；效果图数据必须标“教学模拟”。
7. 保留 r2 的事实修订：tick 60 秒；每日 24 轮是 QUOTA_WAIT；SEND_NOT_LANDED 不是确定未到；gates=[] 空过；DONE 优先可能跳过新待办登记；非底线事项执行端按授权代决；最终用户验收只认用户本人；四道底线不绕过。
8. 代码安全：尽量保持 escapeHtml、可信内置 HTML 集中出口；不引入用户/URL/远程内容。请解释静态扫描 PQ001/PQ005 与 Node/Chromium 实测之间的关系，但不要为了扫描器误报破坏交互。
